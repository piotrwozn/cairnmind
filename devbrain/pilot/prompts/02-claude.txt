This is a fresh session of the second client in the DevBrain pilot, project
devbrain-pilot. You will not receive the previous conversation. Restore the goal
and the current state from the shared memory. Work only in the worktree named by
the packet, with native permissions.

1. MCP resume_context -> read the whole ready packet -> ack_resume with its real
   packet_id, packet_hash and the exact readback of the active plan and task
   {id,version} or null. Read next_task, the sources and the first client's
   checkpoint. State the stage you read and check whether the task is ready for
   testing and review. Do not force the state or reconstruct the plan from
   guesses.
2. Find the implementation and tests based on the memory and sources. Read the
   criteria in the saved task definition; check the number of unittest methods
   it requires, the cases covered and the actual assertions. An empty test suite
   with exit code 0 does not, on its own, meet the criteria.
3. Run the named profile through the client's native tool:
   devbrain check run devbrain-pilot unit --task REAL_TASK_ID
   The command executes code and is subject to your native permissions. Do not
   replace it with a plain subprocess/unittest call and do not create a machine
   result through remember. Read the full run record with
   devbrain check list devbrain-pilot --task TASK_ID
   and the stdout and stderr sources with devbrain source SOURCE_ID. unittest
   usually writes the test names and the summary to stderr. Check the positive
   number of tests required by the criteria, OK, passed=true, the correct
   task_id, the worktree and a fresh check_status. Remember the real run ID.
4. Perform a separate review of the implementation and the assertions. Assess
   each plan criterion; do not treat exit code 0 as a review or acceptance. If
   the code needs to change, make the fix first, refresh the packet/ACK and run
   the profile again for the new fingerprint. Do not reuse an older result for
   changed code.
5. Write the actual review result and the assessment of each criterion to the
   file "$DEVBRAIN_PILOT_REPORT_DIR/review.txt" outside the worktree. Save an MCP
   checkpoint with that assessment, the ID of the successful run, the
   stdout/stderr sources, the scope of the check and any gaps. The checkpoint is
   the client's report, not human acceptance, and it does not replace the runner
   result. Keep the returned source_ids.
6. Only if all criteria are actually met: refresh resume_context and the ACK
   after the checkpoint, read next_task and the current versions. Call MCP
   remember for the existing task with id, expected_version,
   expected_plan_version and:
   metadata={"state":"done","check_run_ids":[RUN_ID],"review_passed":true,
             "review_source_ids":[REVIEW_SOURCE_ID],"acceptance_passed":true,
             "acceptance_source_ids":[CRITERIA_ASSESSMENT_SOURCE_ID]}.
   The last two IDs may point to the same actual checkpoint source_id if it
   contains both the review and the assessment of all criteria. sources must
   include the task's existing sources and every referenced review/acceptance
   source. acceptance_passed here means the criteria assessment; do not
   attribute human acceptance to the user. Moving to done may increase the plan
   version without changing the task definition or invalidating the fresh test
   result.
   Do not send made-up verified/test_passed values or run identifiers.
7. If a test or the review fails, record the real cause and leave
   needs_test/needs_review/blocked as appropriate for the missing work, without
   done. Read the final state and report the plan/task IDs, the sources and the
   remaining gaps.

Every resume_required requires a new read of the packet and an ACK. A version
conflict requires a new read, not an overwrite. After the last status write, do
not modify the code, tests or profile any more. Only the shared memory will be
passed to the next client.
