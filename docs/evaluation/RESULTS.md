**Why the rest of the source counts, not only the quote and the path.** The issue asked for the name in a verified quote or in its path. **What the review of the first version changed, and what it costs.** The first version let an answer pass when two of three names were in the source, did not read a name first in its sentence, and dropped the last letter of any name (so `value.strip()` named "Stripe"); it refused a setting asked with the project's prefix (`CAIRNMIND_PORT`, which the settings file reads as `PORT` with a prefix), a Polish locative or instrumental ("w Ollamie", "z Pythonem") and a short form ("Postgres" for `postgresql`). All of these are changed and covered by tests; the replay above was run on the changed check. Three costs are known and accepted. Every name of a question is now needed, so a name that is only context ("on Linux", "in Anna's note") withholds the answer when the quoted sources do not have it; the refusal lists the names, and the question asked without them is answered. A word first in its sentence is read as a name unless it is one of about 370 listed words that open a question or a request in English or Polish, so an unlisted ordinary word there ("Indexing reads files up to which size?") withholds the answer when the quoted source does not have that word; among the 163 question-like strings of this repository's code, tests and documents the rule reads five such words, all of them prompts of dialogs (four Polish infinitives such as "Usunąć klucz?" and one English verb), none in a question of the sets. A Polish request that begins with an infinitive is the likeliest place for this to happen. And a name that is also a word of the language or of code matches that word: `lambda` in a source names "Lambda", and "JavaScript" names "Java".

**The names checks of 0.13.0 (decision of 22 November 2026).** The owner decided that a lower-case name ("nginx") is not accepted as a written limit. Two checks are built; the names call and the replay of the other one were measured on 22 November 2026 (the table below).

- *The names call.* After a complete answer has passed the citation check and the support check, one more call to the same chat model, with no tools and the schema `{"names": [{"name", "stated"}]}`, lists the product and technology names the answer asserts and says whether a quoted passage states each. A name that is not stated withholds the answer as the support check does: partial, code `answer_unsupported`, the names in the gaps, the answer text never rewritten. A failed or unreadable call withholds it too (code `support_unverified`, "Could not check the names the answer gives."), and so does a call that does not finish in the time limit, which says so. It is made only for a complete answer asked without an answer schema, never in deterministic-only mode (there is no answer there), and it is counted in `model_calls` (phase `names`) like the other calls. The prompt treats the answer and the quotes as untrusted data. It costs one more model call per complete answer. Known gaps: the model may leave a name out of its list, or call a name stated that the quote only resembles; the check cannot be better than the model that reads the quotes, and it reads only the answer and the quotes, not the rest of the source.
- *The names an answer introduces, deterministically* (`unnamed_answer_names` in `src/cairnmind/subject.py`). A name the answer has, by the same written shapes as the subject check, that the question does not have must occur in a quote or in the path of a quoted source; otherwise the answer is not complete (partial, `answer_unsupported`, support_check `names_missing`). It runs after the support check and before the names call, so it saves the names call, not the judge's. It is stricter than the subject check (the rest of the source does not count) and it reads no lower-case name, so it is built but **not switched on** (`CHECK_ANSWER_NAMES` is False) until `scripts/replay_subject_check.py` shows over the kept reports above that it withholds no right answer. It reads only a complete answer: the partial answer that carries the model's own text (the PostgreSQL case of 16 November, status `partial`) is passed by it unchanged, a hole this change does not close.

`docs/evaluation/subject-questions.json` is the set built for these checks: four questions with names the checks must pass, five with the shapes the review named as costs (a name that is only context, an unlisted word first in the sentence, a Polish infinitive), and three about things the project does not have, among them a lower-case product name and a real name on a value the project does not have. Computed without a model: the subject check withholds **5 of the 5** right-answer questions of the cost shapes when the model quotes the right file, and none of the 4 controls (`tests/test_subject.py` pins the missing names for each). That count only confirms the shapes; how often a real model quotes another file, and how often real questions have these shapes, needs the run below.

What each step changes:

- **Quote layout.** A citation was refused when the model copied the words of a passage but not its layout: wrapped lines joined with a space, a Markdown code span without its backticks, a list written with other spacing, a quote of several lines with one left out. Validation now finds the passage of the source that has the same characters in the same order, backticks and the spacing beside punctuation aside (a space between two words or numbers must be there on both sides), and for a quote that skips lines of the source its longest literal run of whole lines, provided every line of the quote is in the source in the quote's order; the quote that is recorded and shown is always the source's own text. A quote written under the source ID of another shown passage is recorded for the one shown source that holds it, and the ID a hit was shown under stands for its source. After the one repair, citations that still fail are left out when another citation of the answer verified; the support check then judges the answer on the verified ones, and the result says in `freshness.warnings` that citations were left out.
- **Definitions.** The lookup missed settings whose name has a word the question does not use: a joining or unit word (`FILES_PER_TRANSACTION`, `poll_seconds`, `MAX_FILE_BYTES`), or a product name written joined in prose (`arcade_version` for "ArcadeDB version"). Such words now stand in a name like filler words, and a name word of five letters or more matches a question word that begins with it. Among candidates that share as many words, a value comes before a function or a class, and then the one whose question word the fewest other candidates have. A synonym (`arcade_url` for "address") is still out of reach. Several of these rules trace to one question each: the rule for a question word that begins a name word serves the ArcadeDB version question of the twenty, a value before a function or class the question about the steps of the knowledge agent, the rarer word among equal candidates the racy window question, and the filler-word rule the default question timeout after the merge. Each is written as a general rule, and no question, accepted answer or file name of either set is in the code, but none has been measured on a question it was not written for. Two side effects are known: a name word of five letters matches any question word that begins with it (a constant `CHECK_SECONDS` for a question about a checkpoint), and a name of one question word and a unit word, from an unrelated file, can take one of the four definition places.
- **Each passage once (taken out).** Chunks of one file overlap, so several of the ten hits can show the same excerpt. Asking retrieval for twenty hits and keeping ten distinct ones changed the order of the first ten as well, because deeper rankings are merged; one question that had passed in every earlier run was then answered from a script that ranked second, complete and wrong. The step was removed. The second look keeps one rule of it: overlapping chunks of a file are read whole once.
- **The second look.** A hit shows 900 characters of a chunk of up to 6,000, chosen by the words of the question, and the line that answers often has none of them (the Java heap is a literal in a list of arguments). When the first pass ends without an answer and a hit was shown in part, the question gets one more pass over the whole chunks of the first hits, without tools, inside the same time limit and context guard. Only a complete answer, validated and judged like any other, replaces the first result. For a chat server on another computer that pass stays inside the rule of #181: a chunk that may not leave the machine is not read whole either. How much it was used, from the recorded calls: before the merge of main (41e70ae) it ran for one of the twenty, the Java heap, in all three runs and answered it. On the trees after the merge (2c27a6b and b5edd80) it ran for none of the twenty in any of the six runs, because the heap is answered at once from the deployment guide; the 18, 18, 18 of b5edd80 does not rest on it. On the final tree (cd6719c) it again ran for none of the twenty in three runs. Of the 22 further questions it ran for three or four in a run and answered one before the merge (the indexing time), one on b5edd80 (the size of the resume packet) and two on the final tree (both of these). Its cost falls on a question that honestly has no answer: one more search and a prompt of about 28,000 to 29,400 characters, under the guard of 32,768 (29,561 at most on the final tree).
- **Definitions first.** The definitions stood at the end of the ten passages and outside the short catalog of the first call, and the model often quoted a passage that uses a value instead of the line that defines it. They are now shown before the hits.

# Store growth (#185)

**Measured on 22 November 2026**, ArcadeDB 26.11.1, one run of the default size before #187 and one after it, on one machine (WSL 2). Both runs used the same seed, so every column but the backup is the same number in both.

**How it measures.** `uv run python scripts/store_growth.py` starts its own ArcadeDB engine on a free loopback port in a new temporary data directory (it refuses to run when an environment variable names another database), and needs Java 21 and the pinned engine but no Ollama or other model. It never uses the default data directory, 8765, 2480 or 11434. It writes, through the product's own `import_history` and `index_project`:

- transcript events in Claude's JSONL format, alternating user and assistant, 500 of each of 200 B, 1 KB and 8 KB of text (`--events`, `--event-sizes`), one step for each size;
- 10 Markdown files of 2 KB, 20 KB and 100 KB in turn (`--files`, `--file-sizes`), indexed once and then revised 20 times (`--revisions`), each revision changing a tenth of the lines of every file, one step for each round.

After every step it embeds every pending chunk through `Retriever.embed_pending` with a fake model that returns seeded pseudo-random vectors of 1,024 numbers (`--dimension`; the repository records the dimension of the default model nowhere, so that number is to be confirmed with `store size --json` on an installation, `vectors.types[].dimension`), and then measures: the rows and bytes of every collection and of every `vector_*` type (`store size`), the vector bytes (`embeddings` plus the `vector_*` types), the size of the database directory, and the size of one gzip backup written by `Store.backup`. The database directory is read with the engine stopped, which the script restarts for the next step, because the engine keeps files it has not written while it runs (about 20 MiB on a nearly empty store in a trial). Bytes per event and per revision are the difference between two steps divided by the events or files written in the second. `--json FILE` keeps the whole report.

**What it does not show.**

- Text is seeded pseudo-random words from one vocabulary of 2,000 words, so its gzip ratio is that of such words, not of real transcripts or code; the transcripts of an installation can compress better or worse.
- Vectors are random numbers: their size in the store is right, but a real model's vectors are not random, and gzip may do slightly better on them.
- Extraction is not run, so the jobs `extract` stay pending and no records, nodes or edges are written; the growth of extracted records, and of the code graph (the files are Markdown, not code), is outside this measurement.
- Bytes of a collection are the length of its rows' JSON form in the engine (`store size`), and above 1,000 rows they are estimated from a sample (marked in the report), not the bytes on disk; the database directory is the bytes on disk, in the engine's own page files, and grows in steps of its page allocation, so a small run shows jumps and even zero or negative figures per unit. Only runs of the default size are to be read.
- A revision of a file replaces its chunks and vectors (#186): what stays is a replaced source row with its full text, so the cost of a revision is that row, its job and the new chunks' difference, not a copy of the vectors.
- One machine, one run, one engine version; no timing is claimed.

# Extraction on Apple silicon (#266)

**Measured on 22 November 2026**, one run on one repository, on the owner's Apple M3 Pro (18 GiB, macOS 27.0.1), with `qwen3.5:9b` in the MLX build under Ollama 0.40.16 (which refuses the `format` field, so the schema goes into the prompt) and `qwen3-embedding:0.6b`, main at 8b912cb. Indexing this repository (550 files) queued 33 extraction jobs. The budget then was 120 s for the whole job (the first call and its one repair), with at most 1,200 output tokens in the first call and 2,400 in the repair.

| | Result |
| --- | --- |
| Jobs | 33, all completed: 21 `ok`, 12 `completed_with_omissions`; none failed on the budget, none needed a second attempt |
| Time of a job | minimum 3.9 s, median 40.5 s, mean 42.3 s, maximum 107.4 s; 5 above 60 s, 1 above 100 s |
| Model calls | 39: 33 first calls and 6 repairs, all repairs successful |
| One call | 22 to 52 s at an input of 6,000 to 8,500 tokens; up to 1,200 output tokens, median 694; about 19 output tokens a second over a whole call |
| Answers cut at the limit | 1 of 33 (exactly 1,200 tokens, `done_reason` length), repaired by the second call |
| Jobs with a repair | six, 78 to 107 s each but one small one; the longest was 52.5 s (the cut call) and 50.4 s (the repair), 107.4 s |

The margin of the longest job was 12.6 s of 120. A cut answer forces the long repair: 1,200 tokens at 19 a second are 63 s by themselves, so a cut call and its repair of about 60 s each are 120 s, and the old budget ends there.

**The new budget is 180 s** (`EXTRACTION_TIMEOUT`). The arithmetic for the measured class of job: a cut call of 63 s and a repair of about the same are 126 s; 180 s leaves 54 s. This is not a worst case: the repair of a cut answer may emit up to 2,400 tokens, about 126 s at 19 a second, and 63 s and 126 s together are 189 s, which 180 s does not cover. The measured repair took 50.4 s. The watchdog of the job worker is the budget plus 5 s (185 s), and the lease of a claimed job is the budget plus 90 s (270 s), so a running job is neither cut by the watchdog before it records its own timeout nor claimed by another worker. The output limit of the first call stays 1,200: one answer in 33 was cut and its repair succeeded, and a larger limit would make every long answer longer.

**What the budget does not do.** The 180 s is the only bound of a job: an extraction call does not use `ask_timeout`, the read limit of the model request for questions (#231), but waits as long as the budget has left (the whole of it for the first call, what is left for the repair, never less than 1 s), on both kinds of model server. A call that takes 63 s therefore completes whatever `ask_timeout` holds. A model that never answers ends the job at 180 s with code `timeout` and `diagnostics.budget.timeout_seconds` 180 (a repair then reports `budget_exhausted`), and a model server that cannot be reached is still `model_unavailable` at once. A hang holds the single extraction worker, and the questions that wait behind it in the same queue, for up to 3 minutes. Extraction jobs are not retried by themselves. Scaling the budget from the model's measured speed would adapt to slower or faster machines, at the price of a calibration call and a number that changes between runs.

The per-call figures (22 to 52 s at an input of 6,000 to 8,500 tokens, median output 694 tokens, 19 output tokens a second, the cut call of 52.5 s and its repair of 50.4 s) come from the owner's raw report of the same run, not from the issue; the figures in the issue are the job times, the counts and the budget.

Not measured: a run with the new budget on the Mac, on this or another repository. The tests with a fake clock show that a cut answer and a repair of 60 s each complete within 180 s and did not within 120 s, and that a job past 180 s still fails with the budget named in its diagnostics; the same two calls of 63 s complete with `ask_timeout` 60 (they failed as `model_unavailable` before the call took its limit from the budget).
