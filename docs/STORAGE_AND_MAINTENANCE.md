# Storage and maintenance

## Data and backups

The default data directory is `~/.local/share/cairnmind` for a new installation. An installation that already has data in `~/.local/share/devbrain` keeps using that directory where it is; nothing is moved or copied. Choose another one with `CAIRNMIND_HOME` or the global `--data-dir` option. Variables are spelled `CAIRNMIND_*`; the earlier `DEVBRAIN_*` spelling is still read. For a configuration variable the new spelling wins when both are set; `cairnmind doctor` reports a pair that disagrees. ArcadeDB data lives in `arcade/databases`. The knowledge service and the engine run in the background for as long as WSL is running. `cairnmind stop` stops the knowledge service; once clients are closed, `cairnmind engine stop` stops the database without deleting data. A [connect-only installation](DEPLOYMENT.md#connect-only-installations) (`CAIRNMIND_ARCADE_CONNECT_URL`) has no `arcade/` folder and no engine: its database runs elsewhere, the `engine install`, `start` and `stop` commands say so and do nothing, and `engine status` reports the server it connects to.

Commands that only read the store never start the engine, create the data directory, configuration or database, or upgrade the schema: `project list`, `records`, `source`, `task list`, `plan list`, `plan show`, `plan next`, `plan contract` without `--write`, `check profiles`, `memory orphans`, `memory extraction-stats`, `impact`, `usage`, `proposed`, `answers list`, `answers show` and `store size`. When the engine is not running, the store was never created or its schema needs an upgrade, they stop at once with one line that says what to run, `cairnmind engine start` or `cairnmind init`. `brief` still starts a stopped engine, as do the commands that write and `check list`, `export` and `backup`. On a connect-only installation no command starts an engine: when the server does not answer, each of them says where it looked.

```bash
cairnmind export ~/memory.json --project my-app
cairnmind export ~/memory.md --project my-app --markdown
cairnmind backup ~/cairnmind-backup.cairnmind.json.gz
```

The ArcadeDB schema stays at version 4, the profile format at 2, and the administrative backup at 5, with support for the earlier formats 2–4. Old plan groups can be adopted explicitly with `plan adopt`, or in the workspace (More, then Old task groups) when a group holds a task a person confirmed. To move a single project, use `memory import`; `restore` replaces the entire store.

Archiving does not wait for the GPU. Status shows archiving, indexing, model processing and the queue separately. The portable backup contains a consistent export of sources and database state; it does not contain credentials, model weights or vectors (#187: the `embeddings` rows and the `vector_*` types are written empty, in the same format 5, and `cairnmind export` leaves them out too). A restore sets the completed embedding jobs back to pending, says how many, and the service rebuilds the vectors from the text; until then search uses the text only and says so, and `cairnmind status` shows the jobs left. A file written by 0.12.0 or earlier still restores with its vectors. How much a backup now saves is measured by `scripts/store_growth.py` ([evaluation/RESULTS.md](evaluation/RESULTS.md#store-growth-185)). Automatic backup runs while the service is running and keeps the seven most recent copies.

**How a restore writes (#362).** `cairnmind restore` and `cairnmind setup local --backup` write a restore in transactions of at most 5,000 rows, 8 MiB of text or 5 seconds open, whatever the size of the store: the engine keeps the pages a transaction changed in its heap until the commit, so one transaction for a store the size of Cairnmind's own repository (81,488 graph vertices and 101,428 edges) ran the engine out of memory on its default heap of 1 GB, and the same restore now passes on that heap (a prototype of the bound also passed on 512 MB). The outcome is still one of two, the whole backup or the store as it was. Before the first row is deleted, the restore writes a mark in the store (`devbrain_meta`, `restore_unfinished`: the backup, the `before-restore-*` copy and that copy's SHA-256; no backup carries it and no restore deletes it) and removes it as its last commit. When a restore fails it puts the store back from the `before-restore-*` copy, after checking the copy's digest, and the error says so; that copy holds no vectors, so the error says what becomes of them as after any restore, by the setting (rebuilt when the knowledge agent is enabled, waiting when it is disabled). When the restore is cut off or killed, or the undo fails too, the mark stays: every command that opens the store, on any installation of it, is refused with one sentence naming the backup and the copy and the two ways out, and `cairnmind doctor` shows `restore_unfinished` and exits 1. On the installation that writes the store, `cairnmind restore FILE` finishes it, or `cairnmind restore` of the `before-restore-*` copy goes back to the rows the store held before (a by-hand restore follows the confirmation rule of [MEMORY_CONTRACTS.md](MEMORY_CONTRACTS.md), so keep the workspace open to keep a person's confirmations; finishing a restore writes no second copy). From another installation of the store, or when the one that started the restore is gone for good, there is a way out that needs none of its files: `cairnmind store takeover --yes` there (a person's act that a marked store allows, and that leaves the mark where it is), then `cairnmind restore FILE` with any valid backup, which replaces the store and removes the mark; the refusal sentence says so. A backup or an export of a marked store is refused, and `cairnmind store prune-backups` keeps the `before-restore-*` copy the mark names (and every such copy when it cannot read the mark) and says so. A failure before the first row was deleted changes nothing and says so, without an undo. When the mark itself cannot be read, what the store holds is not known: no copy is made, a failed restore is not undone and the store stays refused until a restore succeeds. The writer lock is held from the mark to its removal, so another command of the same installation waits instead of committing between two transactions. A transaction that has been open 5 seconds is committed, and a delete that took that long halves the next ones, so on a slow link or a loaded server no request of a restore nears the client's wait of 30 s (the commits of a restore are waited for 120 s, every other commit 30 s); if the engine of a server still takes longer than that, the restore fails, is put back, and says so. A backup is read in pages of at most 1,000 rows in one read transaction and needs no such bound. When the engine runs out of memory or stops answering during a restore, the message says so and names where its heap is set (see [DEPLOYMENT.md](DEPLOYMENT.md#what-to-change)).
A store has one writer: the installation that first opened it, named in the database. An installation is its data directory, identified by `installation.json` there; a copy of that directory on another machine or under another path gets an identity of its own and does not write as the original. A second installation pointed at the same database (for example a server on another host, #72) reads it only: commands that read work, a command that writes stops with one line naming the writer, and its service does not start. `cairnmind store writer` shows which installation writes and what this one is; `doctor` and `status` show the same. To move writing to this installation, a person runs `cairnmind store takeover --yes [--note TEXT]`; the change is kept in the store, the jobs the previous writer was running go back to the queue, and the previous writer stops at its next write. For a store used from one machine nothing changes.

A project removed with `cairnmind project remove` (see [INSTALL.md](INSTALL.md#7-open-your-first-project)) keeps every row in the store: it is counted in `store size`, shown by `status` as `removed_projects`, and written to backups, and a restore brings it back still removed. Its queued jobs wait and run once the project is back. The workspace deletes one (More, then Delete project memory; see below); backups are not changed, so take one first with `cairnmind backup`.

## Deleting a project's memory

Deleting a project's whole memory is a person's act, made in the workspace only (#347). Open it with `cairnmind`, choose More, then **Delete project memory**, and pick the project: the open one is listed first, then the other registered projects, then the removed ones (so a removed project, also one whose folder lies inside the data directory, can be deleted without bringing it back). The workspace reads what would be deleted from the service and shows a consent dialog that names the project and its folder, the counts (records, plans, sources, sessions, check runs, code graph, search passages and vectors), the answer log, and what stays. **Delete** in that dialog is the only thing that sends the deletion. Afterwards the workspace says what was deleted; when the project was the open one it returns to the project list.

- **Deleted:** every row of the project in the store (records and their revisions, sources and the audit notes, passages, vectors, code graph, plans, sessions, acknowledgements, check runs, jobs, memory settings and bindings), its registry row, and its answer log. A new project with the same name and folder starts empty, with a new identity.
- **Not changed:** the backups in `backups/` (only restoring one brings the project back), the project's folders (its `.memory` snapshots, its published memory and the files `cairnmind install` wrote), and every other project, its backups, snapshots and published memory.
- **Refused:** while the project has a session in the workspace that is not known to have ended, or a job in work; on a reader installation (the writer deletes); and for a request that does not come from the open workspace, whatever its token. The checks run before the dialog and again inside the deletion. A coding client started outside the workspace leaves no sign that it runs; its later calls are refused as an unknown project.
- **The command line deletes nothing.** `cairnmind forget PROJECT --delete-project` is refused with exit code 2 and says where the person does it. There is no override flag or variable.
- **The trace:** each deletion appends an entry to the `deleted_projects` list kept in the store (the last 100: the project's id, when it was removed from the registry, when it was deleted, the host, and the counts; never its name or its folder), which `cairnmind status` shows. Backups do not carry it, and a restore does not remove it.

If the workspace cannot open (tmux missing or broken, a store that does not start), the rule does not change and there is no other way to delete one project's memory. First make the workspace work: `cairnmind doctor` names what is missing. Meanwhile `cairnmind project remove PROJECT --yes` takes the project out of the registry (nothing indexes it, names it or archives its conversations; its memory is kept). If the memory must go before the workspace works again, either restore a backup made before the project was added (`cairnmind stop`, then `cairnmind restore FILE`; everything stored after that backup goes too, and without the workspace a person's confirmations become the backup's claims), or remove the memory of the whole installation as [INSTALL.md](INSTALL.md#uninstalling) says: `cairnmind backup DIR/`, `cairnmind workspace stop`, `cairnmind stop`, `cairnmind engine stop`, then delete the data directory. With a database that this installation only connects to (`cairnmind setup remote-db`, or `CAIRNMIND_ARCADE_CONNECT_URL`) the memory lives on that server: deleting the data directory leaves it there.

## How a large code graph is written

Indexing replaces a project's code graph as a whole. A graph of more than 20,000 rows is written in several transactions of at most 20,000 rows each, so that the engine's default memory is enough for it (#377). While those transactions run, and after a write that stopped half way, the project's code graph is reported as not built: `impact`, the memory status and the inspector's graph, groups and neighbors say so, and nothing reads the partial graph as the whole one. The next indexing replaces the whole graph. Before the edges are stored, indexing waits for up to a minute until the engine's index finds the vertices just committed; if it does not, indexing fails with an error that names how many vertices are missing, and no edge is dropped silently. A restore writes a backup's graph in its own, smaller transactions (#362) and waits the same way once, after all its vertices are committed and before its first edge, with no transaction open: the edge transactions begin after the wait. A group of edges that still misses a vertex is committed, waited for and written once more in a new transaction (#396); if that fails, the restore is undone like any other failed restore. If the index keeps missing, putting the store back can fail too: the message then names the safety copy to restore, and the restore mark stays until a restore finishes.

## Store size

`store size [PROJECT] [--json]` reports how large the store is. Like the other commands that only read, it never starts the engine or the service and changes nothing; it prints counts and sizes, never the text of a record or a source. It lists:

- every collection (the tables of the schema, `nodes`, `edges` and each `vector_*` type) with its rows and approximate bytes;
- sources by kind, current against replaced (an earlier version of the same address), and their chunks grouped by the kind of their source in the same way;
- vector rows per embedding namespace, and jobs per state;
- disk use: the whole data directory, `arcade/databases` and this store's database in it, `arcade/engine.log` and its rotated copies `engine.log.1`, `engine.log.2` and so on, the engine's `arcade/log`, the backups in `backups/` (scheduled ones, `before-schema-*`, `before-restore-*` and others, each a count and a size) and the agent journals in `runtime/agents` (sessions and size).

With `PROJECT` the rows are that project's only; `journal_state` and `ingestion_inbox` belong to no project and are shown as store-wide (JSON: `rows` and `bytes` null, `"store_wide": true`), and the disk use is always the whole data directory. Bytes are the length of each row's JSON form, measured in the engine (equal to UTF-8 bytes for ASCII text), so they are close to what the row takes in a backup before compression, not what it takes on disk (except the rows of `embeddings` and of the `vector_*` types, which a backup does not carry, #187). A collection of at most 1,000 rows is summed exactly, and so are one project's rows. Above that, for the whole store, the bytes are estimated from 256 rows, 32 windows of 8 rows at random positions spread over the whole collection, and marked `~` (JSON: `"sampled": true`); the row counts are always exact. The estimate is close when rows of different sizes are mixed through the collection (within about 2% in the tests and on a synthetic store of uneven rows); a collection where a few rows are far larger than the rest can be further off. To group chunks by the kind of their source the command reads one short row per source (id, kind and chunk count, no text), so its time grows with the number of sources: on a test store of 20,000 sources and 80,000 chunks it took about one second, and about one and a half seconds for one project of that store. The figures are not one snapshot: each is its own query, so a row the service writes meanwhile can be counted in one figure and not in another, and chunks whose source was not found are listed as `(source not found)` (JSON: `"source_found": false`). The text form looks like this (from a store filled by the test fixture in `tests/test_store_size.py`; collections with no rows are left out here):

`--json` prints the same data with the keys `project` (null, or `id` and `name`), `method` (`exact_rows`, `sample_rows`, `bytes`), `collections` (each `name`, `rows`, `bytes`, `sampled`, `store_wide`), `sources` and `chunks` (each `sampled` and `kinds`: `kind` (for chunks also `source_found`), then `current` and `replaced`, each `rows` and `bytes`), `vectors` (`types`: `name`, `namespace`, `dimension`, `project_id`, `rows`, `bytes`, `sampled`; `namespaces`: `namespace`, `types`, `rows`, `bytes`, `sampled`), `jobs` (state to count), `disk` (`data_dir`, `databases`, `database`, `engine_log`, `old_engine_logs` (the rotated `engine.log.<n>` copies), `engine_logs`, each `path`, `exists`, `files`, `bytes`; `backups` with `path` and `scheduled`, `before_schema`, `before_restore`, `other`, each `count` and `bytes`, and `safety`: each safety backup with `name`, `kind`, `bytes` and `modified`, newest first; `agent_journals` with `path`, `exists`, `sessions`, `files`, `bytes`), `elapsed_seconds` and `text`. A size is `null` (text: `unknown`) when it could not be estimated.

## Replaced sources and what else is kept

When a file is edited or deleted, its earlier version stays as a replaced source with its full text and hash, so evidence that cites it can still be read and checked; its chunks and vectors are deleted with the replacement, since search never reads them. A store written by an earlier release still holds such chunks (`Chunks by source kind`, column `replaced`). `store drop-replaced-chunks [--batch N] [--max-batches N]` deletes them, for every project in the store (it takes no project), and prints how many rows went (`removed`: `chunks`, `embeddings`, `vector_rows`; `sources`, `transactions`, `complete`). It deletes at most `--batch` rows (default 200), chunks or left-over vectors, per transaction, so other writes are not held up for long; `transactions` counts every one of them. It can be stopped and run again, and `complete` is false when `--max-batches` stopped it with rows still to delete. No source, record or other evidence is touched. Restoring a backup made before the clean-up brings those chunks back; run it again afterwards.

What else is kept without end is bounded as follows:

- Safety backups. The store copies itself to `backups/before-schema-*` before it upgrades its schema and to `backups/before-restore-*` before a restore. Nothing deletes these on its own, and the daily rotation (which keeps the last seven scheduled backups) never counts them. `store prune-backups --keep K` deletes all but the newest K of each kind: it prints the files it would delete and those it keeps, and asks before deleting (`--yes` skips the question). Only a person in their own terminal can run it; inside a coding session, or without a terminal, it deletes nothing. A file written again after the list was shown is left in place. Scheduled backups and backups you named yourself are never touched.
- Job history. Every job row stays, because later work reads it: a job's key stops the same extraction or embedding from being queued again, `status` and the job summaries count jobs by state, import coverage reads the import job, and a held or all-rejected extraction can be queued again. What goes is the attempt history of completed jobs that last changed more than `job_history_days` ago (`config.json`, default 30, 0 keeps it): once a day, right after the daily backup, the writer installation empties it and keeps how many events there were (`jobs show` still counts them). Failed, pending and running jobs keep their history.
- `arcade/engine.log`. When the engine starts and the log has reached `engine_log_bytes` (default 10 MiB), it is moved to `engine.log.1`, older copies shift up, and `engine_log_copies` of them are kept (default 3). The engine therefore always starts on a log under the limit; one long run can still write past it until the next start. If the filesystem refuses the rotation, the engine starts anyway, appends to the old log and writes a line there saying why.
