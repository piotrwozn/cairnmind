# Changelog

All notable changes are listed here, newest first. Releases up to 0.8.0 were published as DevBrain.

## 0.11.0

### Confirmation: only a person confirms

- Only a person can store a record as confirmed. A coding session, an MCP client, the built-in agent and a session's finding that ask for the status confirmed are refused with a message that says what to do: store the record as proposed and confirm it in the inspector (#177).
- A coding session, an MCP client, the built-in agent and `POST /remember` can no longer change, replace (`supersedes`) or set another status on a record a person confirmed, and records confirmed before 0.11.0 are kept the same way, because nothing says a person did not confirm them. The write is refused with HTTP 400, stores nothing, names what would differ and tells the caller to store a new proposed record that names the confirmed one in `metadata.possible_conflicts`, so the person decides in the conflict inbox. Writing under the key of a confirmed record gets the same refusal. Any other key clash names the record that holds the key, and `cairnmind remember` says to use another key or to dispute or decide that record in the inspector (#177, #238).
- A write that changes nothing of what a person confirmed only adds the sources it cites and does not put an external session's origin mark on the record (#177).
- Progress on a confirmed task and a new checkpoint are stored as before; a confirmation a package brought can still lapse when a session changes the record, and a disputed record can still be changed by a session (#177).
- A plan save that changes or removes a step a person confirmed is refused and names the step and the field; so is a session's save that changes the title, goal or constraints of a plan while a step still carries the confirmation given with the plan. A save that adds steps or changes unconfirmed steps is stored, and `cairnmind plan save` or `cairnmind plan adopt` typed in a person's own terminal can change them (#177).
- A plan and all its steps can be confirmed in one act, with `cairnmind memory confirm-plan` or the inspector API (#170).
- `cairnmind remember --confirmed` and `cairnmind memory confirm-plan` work only in your own terminal, outside a coding session; anywhere else they are refused. `cairnmind task add` adds a confirmed task in your own terminal and a proposed one anywhere else, and prints which. This check does not stop a program that runs as you and fakes a terminal; docs/MEMORY_CONTRACTS.md says exactly what it does not cover.
- The refusals of `remember --confirmed`, `record-kind accept/withdraw`, `memory confirm-plan`, `task add`, `store prune-backups` and the `plan save` refusals for a confirmed plan or step say when input or output that is piped or redirected is the reason they do not count as a person (#239).
- `cairnmind plan adopt` on tasks a person confirmed, or tasks added with `task add` up to 0.10.0, works only in the person's own terminal and says so when refused elsewhere; the refusal names the task by its text, and the refusal for a confirmed checkpoint record points to the checkpoint tool (#177, #239).
- At the upgrade to 0.11.0, a record that was confirmed before only a person could confirm is marked as confirmed by a person when a review audit or workspace form written on this computer covers it and the record still says what the confirmed version said. A 0.10.0 audit holds no name, so such a record shows "the local user". `cairnmind init` reports how many records were marked and how many stay before the rule, and `cairnmind restore` runs the same step over the records that a backup made before 0.11.0 brings back (#215).
- The other records confirmed before this version keep their status and are shown as confirmed before only a person could confirm, with no claim about who confirmed them. You can confirm such a record in the inspector to make it yours.
- The inspector's record view, its conflict view and its lists, `memory show`, record lists, the search hits the `ask` model reads and the resume packet say who confirmed a record (new field `confirmed_by`).
- Reviews, conflict decisions and typed findings now record the person's Git name, branch and commit, and hash the record's kind, key and the record it replaces. Reviews, conflict decisions and plan confirmations also record a hash of the passage the record quotes, so a quote changed by hand in a published file is refused. A confirmed record that no person's act covers can be confirmed again in the inspector (#170, #172).
- Confirming a record already confirmed here, or disputing one already disputed, now says so instead of reporting a version conflict, in English and Polish (#239).
- Fixed: the inspector treated a record as covered by a person's workspace form when any client had sent `metadata.origin: workspace_form`.

### Team memory

- Confirmed knowledge can be published with a branch as one readable file per record or plan under .memory/cairnmind-published/, with `cairnmind memory publish`. `--preview` shows what would be written (#170).
- `cairnmind memory import-published` imports a merged published directory. New records are added and known ones fast-forwarded. Diverged ones are refused with their paths, or taken with --take-published. A file can never attach this machine's own sources to a record, and nothing imported is shown as verified (#170).
- `cairnmind memory import-commit REVISION --project P` imports the published memory of a commit, such as the main branch after a merge, and checks every quoted passage against that commit's code. A passage still there anchors its record; one that is gone leaves it orphaned in the output and the inspector. Only a passage that a person's review recorded is compared. A repeat import changes nothing, and nothing imported is shown as verified (#172).
- `cairnmind memory diff BASE HEAD` summarizes how the published team memory differs between two commits, read from Git with no store or model. It lists decisions, constraints and facts added, changed, disputed, superseded, reverted or withdrawn, tasks opened and closed, and plans redefined, each with its text and quoted source. `--markdown` gives a bounded pull request comment in which record text cannot add markup, mentions or links (#172).
- A Team memory workflow posts that summary as one pull request comment and updates it on every push. It fails when the published memory directory would not import, and needs only the default token (#172).
- `cairnmind memory check-published` checks a published directory without a store or service. It refuses conflict markers, hand-merged or hand-edited files, contradicting revisions and supersessions that nothing replaces, and names each path. It exits 2 when the path is not a directory, and names an empty file, an invalid kind, an invalid id or a created_at without a time zone separately (#170, #239).
- `cairnmind memory show-published` reads a published directory as text (#170).
- Publishing team memory refuses, before writing anything, a record or quoted passage that holds a secret registered with Cairnmind, the values behind the env: references of the saved connection and memory model profiles, a private key block, a well-known key or token shape, a bearer token, a password in a connection string or a long random string, even when an invisible character splits it. It names the file, the field and the kind of hit and prints nothing of the secret, so `cairnmind memory publish` no longer needs CAIRNMIND_ENABLE_PUBLICATION (#171, #182).
- E-mail addresses, phone numbers and a project's own patterns can be kept out of published memory with `.cairnmind/publication.toml`; they are off by default. A teammate's file that trips them is reported by `memory publish`, never rewritten and never a reason to refuse (#171).
- `cairnmind memory release PROJECT RECORD --reason TEXT` lets a person publish a record whose hits are false alarms; the reason is published in the record's file and covers only the exact values it names. A registered secret is never released, and the publish refusal for one no longer advises `memory release` but says what to do instead (#171, #239).
- `cairnmind memory check-published` and `memory import-published` refuse published files that hold such a value, so a CI job can fail a pull request that adds one by hand, and `check-published` lists every release for the reviewer; an example workflow is in docs/examples/published-memory-check.yml (#171).
- An imported record keeps that it was confirmed and is shown as confirmed elsewhere, with who the package says confirmed it and where it came from; it is never shown as your own confirmation and is not verification. The dry runs of `memory import`, `memory import-published` and `memory import-commit`, and the import dialog, say how many such records a package brings.
- A memory import is run only by a person: inside a coding session `memory import`, `memory import-published` and `memory import-commit` are refused, except their dry run.
- An import that would replace a record you confirmed or disputed on this computer with another text or status is refused and lists those records; the new option `--replace-confirmed` applies it, and the import dialog states the number before you apply. An import that only moves such a record on (task progress) keeps your confirmation.
- After a person keeps one finding of a pair in the conflict inbox, published memory carries the rejected finding, with its text and cited sources, as superseded by that decision instead of leaving it confirmed or holding both. This also applies when the person keeps the confirmed finding against a session's proposal, and when the kept finding is held back. A rejected finding of external origin is still never published (#239).
- A decision a person keeps in the conflict inbox is now published when the other proposal can never be published (it came from an external session, cites a source an external session wrote, or has a non-canonical ID); the supersession is recorded on both records, and the proposal stays unpublished (#239).
- Importing published memory into an empty store no longer fails when a replacement's ID sorts before the record it replaces; the supersession is kept whatever the order of the two IDs (#239).
- The publish preview says why a replacement a person kept in a conflict decision is still held, lists records published as superseded while their replacement is held, and names an external session's record as such when a record that names it is held. `memory publish` tells a record confirmed in a terminal from a proposal in the held list, and shows each held record's key and the start of its text, cleaned for the terminal; both are left out when they hold a value the secrets gate refuses (#239).
- `memory publish` writes again a published file that went missing instead of refusing, and a remaining refusal names `git checkout -- <path>` (#239).
- `memory diff` and `memory import-commit` name an unknown revision instead of printing 'no message' (#239).
- `memory import` of the store's own latest snapshot is unchanged, and its refusal now tells a diverged history from local knowledge that changed (#239).
- Each project can choose where its published memory goes with `cairnmind memory carrier PROJECT --repository | --checkout PATH`: its own repository (the default) or a checkout of a separate memory repository, which receives the same package under the project's identity. Cairnmind still never stages, commits or pushes (#173).
- Changing the carrier moves nothing: the command says where the earlier package is, how many files it has and what to do with it. `cairnmind memory status` shows where the published memory is and whose it is, the carrier, any package left in the repository, and what the previous carrier still holds (#170, #173).
- A checkout path must be a plain, real absolute directory in a Git checkout. These are refused: a symbolic link anywhere on the path, control characters, and a path inside Cairnmind's data, a registered project's files or any project's memory. So is a path that contains a registered project or shares its Git repository. The path is checked again at every publish (#173).
- Publishing into a checkout that already holds other packages is refused for a project that has none yet. It must first import its package, or start a new one with `cairnmind memory publish --new-package`, which also works with `--preview` (#173).
- A project registered at a subdirectory of a repository now has its own code state, checks and scope, covering only the files below it: an uncommitted edit outside that directory does not make its checks stale until the next commit. A subdirectory the repository ignores, or one with no file Git lists, stays unknown (#174).
- The memory directories of projects registered below another project are left out of its indexing, code fingerprint, scope and impact checks, in every worktree of the repository, so writing one project's memory no longer makes another project's checks or acknowledgements stale (#174).
- `cairnmind memory import-published` refuses the published directory of another project in the same repository, also through a symbolic link or a differently cased name: each project imports only its own, and the refusal names the directory as the reason, with or without `--bind` (#174, #239).
- docs/MEMORY_CONTRACTS.md describes one memory directory per project in a repository, what a subdirectory project's checks do not see, and a CODEOWNERS pattern so each team reviews its own memory (#174).

### A database on another host

- Connect-only installations: with arcade_connect_url (CAIRNMIND_ARCADE_CONNECT_URL) set, or a database address that is https or on another host, Cairnmind only connects to a database that runs in a container, on a server or in Kubernetes; it never installs, starts or stops an engine, never creates a database, generates no database password and needs no Java. It never writes that host's password into the data directory, and when the server cannot be reached, it says so (#68, #72).
- The first command that runs with CAIRNMIND_ARCADE_CONNECT_URL set saves the address in config.json and says so, so a command started later without the variable stays connect-only instead of starting a local engine; remove arcade_connect_url from config.json to go back to the managed engine (#68).
- A database on another host must be reached over https with the certificate verified, against a private authority named by arcade_ca_file or the system's authorities (which SSL_CERT_FILE and SSL_CERT_DIR replace when set); plain http is refused there, and verification cannot be turned off (#72).
- The user root and a password stored in config.json are refused for a database on another host, and the message says which rule was broken (#72).
- The database password can come from CAIRNMIND_ARCADE_PASSWORD or a private file (mode 0600) named by arcade_password_file, and a password, URL or user taken from the environment or a file is no longer written to config.json (#72).
- A database password file mounted from a Kubernetes Secret is read. Its links are followed only in the kubelet's exact layout, to a regular file of your user that group and others cannot read. Every other link is still refused with a message naming the rule, a password file that cannot be opened says why, and an arcade_password_file that names a folder is refused with the setting and the rule, instead of "[Errno 21] Is a directory" (#211, #242).
- New command `cairnmind db create-user --admin-password-file FILE` signs in as root once to create the database and a user with rights on that database only. It can be run again for the same user and database and reports that nothing was created. It creates the missing database of a user that exists without one. For a user that already exists and cannot use the new database, it stops with what to do and leaves no empty database behind (#72, #242).
- A store has one writer, the installation that first opened it, named in the database; another installation that points at the same database reads it only, and a command that writes stops with one line naming the writer (#70).
- An installation is identified by installation.json in its data directory, so a copy of that directory on another machine or under another path gets an identity of its own instead of writing as the original (#70).
- `cairnmind store takeover --yes [--note TEXT]` lets a person move writing to this installation; the change is recorded in the store, the previous writer's running jobs go back to the queue, and the previous writer stops at its next write. It also works when this release cannot read the store as a reader, for example when its schema belongs to another release (#70).
- `cairnmind store writer`, `doctor` (store_writer) and `status` (writer) show which installation writes the store and whether this one is the writer, a reader, or has lost the role; `store writer` and `doctor` also show the note given with `store takeover --note`, as inert text. `status` shows that block only from the running service. On an installation that only reads the store, `status`, `jobs list`, `jobs show` and `memory status` say so and name `cairnmind store writer` and `cairnmind doctor`, instead of telling it to run `cairnmind serve` (#70, #242, #244).
- The service does not start on an installation that only reads the store. A running service pauses its background work when another installation takes over and resumes on its own once writing is taken back. Starting a service that exits at once now reports its last log line instead of waiting a minute (#70).
- On an installation that only reads the store, a refused write says its reason once instead of twice, backup and export no longer print the refusal-like notice, and `cairnmind retry-jobs` is refused even when nothing failed (#244).
- `cairnmind store takeover` without --yes suggests what fits the role: nothing on the writer, starting the engine when the role cannot be read (#244).
- Two installations that open a new database, take over writing a store or claim a new one at the same moment now always end as one writer and one reader: the second is refused as a whole and told to run `cairnmind store takeover --yes` again, instead of failing with the engine's 'Concurrent modification' message or sometimes leaving the writer row and the journal head naming different installations. A takeover that overlaps a write of the current writer is refused the same way, with a message that says so (#68, #70).
- `cairnmind store writer`, `doctor` and the service status report a store whose writer row and journal head name different installations; until the next `cairnmind store takeover --yes` repairs it, the installation the row names is refused every write and runs no schema statement or upgrade (#70).
- Two installations that create one store at the same moment no longer leave two schema_version or lookup_indexes rows in it (#68).
- On a connect-only installation `cairnmind engine install`, `start` and `stop` do nothing and say so in one sentence (exit status 2), whether or not the knowledge service runs; `engine status` shows the mode, host, user, encryption and the server's version without looking for Java (#68).
- A server whose ArcadeDB version this release does not support is refused by every command, `cairnmind db create-user` included, before anything is read or written, with the supported version named; `engine status` exits with status 1 and `doctor` reports it (#68).
- When the database or its user does not exist yet, or the server does not answer, a connect-only installation says where it looked and names `cairnmind db create-user`, instead of starting a local engine or showing a bare HTTP error. When the database cannot be found, the message also names the other cause, a user with no rights on it (#68, #242).
- A refused sign-in to a database Cairnmind only connects to also says that ArcadeDB refuses a user for about 30 seconds after several failed sign-ins, even with the right password. docs/DEPLOYMENT.md and SECURITY.md say the same, and that each database gets its own user from `cairnmind db create-user` (#242).
- `cairnmind engine status` started without the database password is refused (exit 1, "available": null, nothing sent), and `cairnmind doctor` gives `arcadedb.available` as null in the same case instead of reporting a server that does not answer. The message also names arcade_user left at root and an unset arcade_database, on every command and not only the first, and what would be used in their place. On a host other than this machine, the refusal of root also names the missing password and database. docs/DEPLOYMENT.md says the same (#242).
- `cairnmind doctor` shows where storage runs (mode, host, address, supported versions), the database user, whether the connection is encrypted and where the password comes from, and notes when it is stored in config.json; it no longer runs Java on a connect-only installation. `cairnmind status` has a new field `storage`, and `store size` says that the database files are on the server. An existing local installation keeps working unchanged (#68, #72).
- A database address that carries a user, a password, a query or a fragment is refused as before, and is no longer repeated in messages, `engine status`, `doctor`, `status` or `store size`; the refusal names arcade_connect_url when that setting supplied the address (#68).
- The installer skips the Java check and the ArcadeDB download when CAIRNMIND_ARCADE_CONNECT_URL is set (#68).
- `cairnmind eval run`, `eval memory` and `eval repository` are refused on a connect-only installation, because they create and drop databases (#68).
- A container image for the pinned ArcadeDB release and a Compose file to run the database on a server or a laptop, with the root password read from a file and the port kept on loopback (#73).
- The database image of deploy/arcadedb runs ArcadeDB in production mode: no Studio, error details only in the server log, the write-ahead log flushed on commit. It leaves out the MCP plugin, so /api/v1/mcp does not exist. docs/DEPLOYMENT.md says what the server exposes and to whom. The local engine is unchanged (#211).
- Plain Kubernetes manifests for the database in deploy/kubernetes: a StatefulSet with its volume, a headless Service on the server's own TLS port, a NetworkPolicy, probes from the image's health check and a Secret template with no value in it. docs/DEPLOYMENT.md documents them with TLS, the dedicated user, and backup and restore (#211).
- New guide docs/DEPLOYMENT.md: running the database in a container, connecting Cairnmind to it, logical backups and volume snapshots and what each leaves out, and what to do when the pinned ArcadeDB version changes. A section leads from nothing to a working connect-only installation for the Compose server, for Kubernetes through a port-forward and for a client inside the cluster, and says which installation writes, where backups go and what a dropped connection leaves behind (#68, #73).
- Measured for a database reached over a connection, with client and server on one machine: indexing Cairnmind's own source (128 files) takes 2,313 database requests the first time and 8,101 after every file changed; with 20 ms added to every request that is 65 s and 229 s instead of 17 s and 64 s through the same TLS endpoint (#68, #167).
- New CI jobs that are not required checks: deployment-image builds the database image, moves a backup between two copies of the Compose file and checks a volume snapshot; kubernetes-manifests checks the manifests against a kind cluster's schemas, applies them, verifies that the NetworkPolicy lets labelled pods reach only the TLS port and keeps every other pod out, and runs the connection check, a logical backup and restore, and a volume snapshot restore. Both run as connect-only installations with the dedicated database user, and the Kubernetes check indexes from inside the cluster and takes over writing from the workstation (#68, #73, #211).

### Models and where memory goes

- The knowledge agent can use another model or model server: `cairnmind models set` chooses the chat model (answers, extraction) and the embedding model separately, each on the local Ollama, another Ollama, or any server with the OpenAI-compatible API such as LM Studio, vLLM or llama.cpp, after one test call to it; it changes only that role in the settings (#67).
- A model server on another computer needs HTTPS and your explicit `--allow-remote`, because it receives memory content; keys are named with `--credential-ref env:NAME` or `profile:ID` and are never stored in the settings or in memory (#67).
- Every source and record has a sensitivity class (project, conversation or third_party), derived from its kind and origin mark and stored nowhere. A record takes the highest class of the sources it or any earlier version cited, so an update never lowers it. The inspector, read_source, memory_records, the terminal detail view, `cairnmind memory show` and `memory show --sources` show it (#180, #241).
- A memory model server on another computer receives only the sensitivity classes listed in the new setting memory_remote_classes, by default project only. Extraction leaves other sources pending (remote_not_allowed), embedding leaves their chunks to full-text search, and ask leaves them out of its context and counts them under held_back. Held extractions and embeddings run once a class is added to memory_remote_classes and the service is restarted, without importing anything again (#181).
- With the local Ollama, extraction, embedding and ask send exactly what they sent before (#181).
- `cairnmind doctor` shows, under `memory_models`, which server and model each role uses, whether it answers, where its content is sent, which sensitivity classes it receives and which stay on this computer, and whether this pair of models has passed the evaluations; `cairnmind models set` shows the classes too, and doctor reports an invalid memory_remote_classes (#67, #181).
- A passing `cairnmind eval run`, `eval memory` or `eval repository` is recorded for the exact pair of models and setup (servers, context window, reasoning effort) it ran with; answers given with models other than the release's carry `model_evaluation: unevaluated` in their diagnostics until recall and memory have both passed (#67).
- After a change of embedding model, `cairnmind models set` says that vectors must be rebuilt with `cairnmind rebuild-vectors`; vectors of different models are kept apart (#67).
- An embedding model on an OpenAI-compatible server, which reports no digest, is checked with one fixed sentence when the service starts and before rebuild-vectors. If other weights are served under the same name, doctor reports it (also while the server is down), no new vectors are made and search uses text only, until rebuild-vectors accepts the new weights under a new vector namespace (#67, #212).
- When chat and embeddings run on different servers, one that is down no longer holds back the other's background work (#67).
- `cairnmind models pull` downloads only the models that run on the local Ollama (#67).
- The recall evaluation was run with the embedding role on a server the product treats as remote. With the default memory_remote_classes, 21 of the fixture's 22 chunks (all conversation) were not embedded, and recall stayed at 20 of 20 in eight of nine runs (19 in one). The fixture's questions use words from their answers, so it cannot show what vectors add (docs/evaluation/RESULTS.md) (#181).

### Answers about a repository

- `ask` no longer gives a complete answer about a product or setting that the quoted sources never name: a check that asks no model looks for every name the question uses for its subject (a capitalised name, an identifier, a word in backticks) in the quotes, their paths and their sources, and withholds the answer with `answer_unsupported`, listing the names, when one is missing. A name that is only context (an operating system, a person) withholds the answer too when no quoted source has it. Not read by this check: a name written in lower case without backticks, a word in capitals, a question in headline case; not caught: a name the quoted file has elsewhere than beside the quoted value (#245).
- On Cairnmind's own repository the twenty questions give 19, 19 and 20 of 20 complete and right in three runs with the default models, and 20 in the run of the release gate, with none complete and wrong, against 13 in the worst run before this work; of twenty-one questions about things the repository does not have, 20 are refused, and the one left, which names its subject in lower case, is answered complete and wrong. The default chat model stays qwen3.5:9b (#104, #245).
- `cairnmind eval repository` accepts questions about things a repository does not have (`"answer": {"absent": true}`), which are right only when they are refused; an ask that broke (timeout, unavailable model, invalid JSON) is counted as `absent_failed`, not as a refusal. Cairnmind's own set of twenty-one is `docs/evaluation/absent-questions.json` (#245).
- A citation is accepted when the model copied the words of a passage but not its layout (joined lines, other spacing beside punctuation, a code span without its backticks, lines of the source left out between quoted lines); every line of the quote must be in the source, a space between two words or numbers is still compared, and the quote recorded and shown is always the source's own text (#104).
- A cited quote may now be as long as the 900-character passage shown to the model, so an answer about a setting whose value sits at the end of the passage is no longer left unverified (#241).
- A quote written under the ID of another shown passage, or under the ID a search hit was shown with, is recorded for the shown source that holds it; after the one repair, citations that still fail are left out when another citation of the answer verified, and the result then says so in `freshness.warnings` and counts them in `diagnostics.citations_dropped` (#104).
- When the first pass of a question finds no answer and a passage was shown only in part, the best passages are read whole once more, without tools and inside the same time limit; the diagnostics say `second_look`, and for a remote chat server that pass holds back the same memory as the first (#104).
- Definitions are shown to the model before the search hits, so the line that states a value comes before the passages that use it (#104).
- Keys of TOML files (pyproject.toml and others, not lock files) are definitions, so a question about the required Python version or the project version is shown the line that states it. A TOML file nested too deeply to be read is reported as invalid and does not stop indexing. `cairnmind impact` compares a changed TOML file key by key instead of treating it as a file it cannot compare (#104).
- Parameter defaults of Python functions are definitions, shown when the question names the parameter or spells its name in the question's words. `cairnmind impact` compares a parameter by its own text, so a change to its neighbour or to the decorator does not mark it as changed (#104).
- A setting whose name shares one word with the question is shown when its file or class shares another word with it, such as a timeout constant in journal.py for a question about the journal timeout (#104).
- The definition of a setting is found when its name has a unit or joining word the question does not use (per, seconds, bytes, tokens) or a product name the question writes joined; among equal candidates a value comes before a function or class, and a name that is only a filler word such as DEFAULT is no longer taken for the setting asked about (#104).
- `cairnmind eval repository` accepts a value in megabytes written in whole gigabytes where a question lists the form `{gb}`, and docs/EVALUATION.md says how to measure another chat model or a larger context window (#104).
- `cairnmind ask --log`, or `"answer_log": true` in config.json, keeps each answer with its question, citations (source id, sha256, quote), commit, status, model digest and timings in a private per-project log outside the database, so a logged answer is never evidence (#15).
- `cairnmind answers list`, `answers show` and `answers prune` read and trim the answer log; it is capped at 8 MiB per project and deleted by `forget --delete-project` (#15).
- `cairnmind eval replay PROJECT` asks the logged questions again for the scope they were logged with and reports answers that are no longer complete or no longer cite a source they cited, comparing evidence, not wording (#15).

### Extraction

- Memory extraction no longer turns the protocol of a session into proposed records. The launcher's first message, Codex's environment block and a client's tool calls are left out, and conversation messages are told that requests to the assistant, one-off questions and the assistant's narration of its own actions are not project knowledge. On the new evaluation set the share of proposals a person would reject fell from 65% to 29%, with no kept record lost (#160).
- Automatic extraction no longer reads the block that `cairnmind install` writes into AGENTS.md and CLAUDE.md, also in a file saved with a byte order mark, so the client protocol no longer becomes proposed tasks and constraints; records extracted from now on carry extractor version 2 (#241).
- A model that returns depends_on: null no longer makes the whole extraction of a message fail; null is stored as no dependencies (#238).
- Every record that automatic extraction writes now carries metadata.extractor: the extractor version, a hash of the prompt and schema, and the model as name@digest (name@unknown when the model server gives no digest or does not answer in time). Clients can read it but cannot set or change it. Portable memory carries it, keeping only a well-formed stamp on an extracted record. Extracted records without it count as version 0 (#192).
- `cairnmind memory extraction-stats PROJECT [--json]` and `GET /inspector/extraction-stats` show, for each extractor version, how many automatically extracted records are still proposed, confirmed by a person here, disputed or superseded, and the share confirmed of those reviewed, read from record revisions without a model (#193).
- New command `cairnmind eval extraction` measures, with the local model, what extraction proposes from built-in agent, Claude Code and Codex conversations against the records a person would keep. Its report contains the same extractor stamp, so an evaluation result can be matched with records in real projects. The evaluation runs on the configured chat model server, as extraction does, also with a model profile (#160, #192).

### Store, backup and indexing

- Restore writes the rows of a backup in groups of a few hundred per request instead of one row at a time. For the store of Cairnmind's own source it now takes 1,140 requests and 18 s on loopback instead of 281,451 requests and 239 s; into an empty database with 20 ms added to every request it takes 1,079 requests and 28 s, so a large store can be restored over a network. Each group is limited to 250 rows or about 1 MiB of JSON. Nothing else changes: what is restored, every check made before anything changes and its message, and the rollback of a restore that fails or is cut (#219).
- Each answer from the database is freed as soon as it is read instead of waiting for Python's garbage collector, which keeps the memory of restore bounded now that it sends larger requests (#219).
- Restore reads a backup in pieces instead of loading it whole: it checks the checksum and every cross reference in two passes over the file before it changes anything, so its memory no longer grows with the size of the rows; a small index of ids (about 100 MiB per million sources, records or graph nodes) remains. The file format is unchanged (#196).
- The whole-database backup (the daily backup, cairnmind backup and the safety copies made before a restore or a schema change) is written as a stream, so its memory no longer grows with the store. The file format is unchanged and earlier versions restore it (#196).
- A backup file appears only after the backup's transaction has committed; the store size view counts temporary files left by an interrupted backup, and the service removes them after a day (#196).
- Restore refuses a backup file that changes while it is being restored, and the store stays as it was; the refusal says that the file changed while it was being read, instead of calling the file corrupt or reporting a checksum mismatch (#196, #238).
- `cairnmind restore` refuses a missing path or a folder before anything starts, instead of calling it a corrupt backup (#244).
- `cairnmind backup DIR/` with a trailing slash creates the folder (readable by you only) and writes a dated file in it, instead of a file named DIR. A backup into a folder that cannot be created or written says 'Cannot write a backup into <folder>: <reason>' instead of a raw error naming a temporary file (#238, #244).
- `cairnmind store size [PROJECT] [--json]` reports how large the store is: rows and approximate bytes per collection and vector type, sources and their chunks by kind (current against replaced), vector rows per namespace, jobs per state, and the disk use of the database, backups, agent journals and engine log. For the whole store, bytes above 1,000 rows are estimated from 256 rows spread over each collection; one project's rows are summed exactly. It is read-only, starts nothing and prints no record or source text (#184).
- `store size` lists each before-schema and before-restore safety backup with its size and time, and counts the rotated engine.log copies. It shows a vector type left empty by a restore as 'unregistered, empty (left by a restore)' instead of the namespace '(none)' (#190, #238).
- `cairnmind store prune-backups --keep K` deletes all but the newest K safety backups of each kind, after showing them and asking, and only for a person in their own terminal (#190).
- Once a day, after the daily backup, completed jobs that last changed more than job_history_days ago (default 30, 0 keeps everything) lose their attempt history; every job row, its key and its counts stay (#190).
- At each engine start an engine.log that has reached engine_log_bytes (default 10 MiB) is moved to engine.log.1, keeping engine_log_copies old logs (default 3); if the filesystem refuses the move, the engine starts anyway and appends (#190).
- engine.log is created private (mode 0600) whatever the umask, and when it is rotated the old copies are made readable only by their owner too; a copy the owner cannot open or change is still rotated as before (#238).
- An engine_log_bytes or engine_log_copies in config.json that is replaced by its default is reported on standard error and in engine.log when the engine starts, and `cairnmind doctor` lists it among its environment notes (#238).
- When a file is edited or deleted, the chunks and vectors of its earlier version are deleted in the same transaction. The earlier version keeps its full text and hash, so evidence that cites it can still be read and checked. A portable memory import no longer creates chunks for source versions that are not current. So `cairnmind status` counts fewer chunks and indexed sources (#186).
- New command `cairnmind store drop-replaced-chunks` removes the chunks that earlier releases kept for replaced sources. It covers every project in the store, works in short resumable transactions of at most `--batch` rows, and reports how many rows it removed (#186).
- Indexing writes the code graph 250 rows per database request instead of one statement per row, so indexing this repository's own source again after every file changed took about 7,000 requests instead of 57,000 in the measurement made for this change, which is not the 128-file measurement of the deployment guide (#167).
- Indexing also removes graph nodes that no longer exist in groups, so indexing this repository's own source again after half of every file's functions were deleted takes about 5,400 database requests and 27 seconds instead of 67,500 and 75 seconds (#167).
- Indexing files that replace a current source, and files that were deleted, now counts first what the old source leaves behind and writes each file in one transaction, up to eight small files together. The journal events of a transaction are stored in one statement. After every file of a project changed, indexing again needs about half the database requests and time on real code (Cairnmind's own source: 47% of the requests, 50% of the time), and about a quarter to a third on trees of very small files (#102).
- `cairnmind memory status` checks only the newest manifest, so it answers quickly for a large project; its `latest` reads `manifest_valid` with `objects_checked: false`, and `memory inspect` and import still check every object (#161).
- `memory status` now shows the size of the portable package, its rows, bytes (UTF-8, as a snapshot counts them), manifest bytes and largest object, against each publication limit and warns from 70% of any of them, before publishing stops (#191).
- Jobs that the model runtime refused or did not answer in time are labelled model_context_length, model_timeout or model_runtime_error instead of legacy_job_error, and the catch-all label is now job_error (#238).

- An acceptance criterion can name the check that proves it: write it as `{"text": ..., "check": PROFILE}`. `check_status`, `cairnmind plan next` and the new `cairnmind plan contract PROJECT` list each criterion as `machine_fresh`, `machine_stale`, `machine_missing`, `machine_unknown`, `manual_pending` or `manual_reported`. `plan contract --write CODE` adds check profiles from commands proposed with the criteria; the code is printed with the diff and names exactly the proposal that was shown. It runs nothing and never changes a declared profile (#13).
- The names of running processes are `cairnmind` now: terminal sessions and their sockets, the identity the service and the broker announce, cookies and temporary files. Whole-database backups are written as `.cairnmind.json.gz`; `.devbrain.json.gz` files are still restored. Because a new version does not find a workspace started by an earlier one, the installer stops the broker and the service of the installed version and refuses to continue while a workspace is running (#40).
- **The names a project shares are `cairnmind` now.** The MCP server in `.mcp.json` and `.codex/config.toml`, the markers in `AGENTS.md` and `CLAUDE.md`, snapshots in `.memory/cairnmind/` with the format name `cairnmind-portable-memory`, and check profiles in `.cairnmind/checks.toml`. `cairnmind install` converts what an earlier version wrote where it stands, keeping tool approvals; snapshots in `.memory/devbrain/` and profiles in `.devbrain/checks.toml` are still read. Versions up to 0.9.0 do not read the new names, so everyone who shares a repository upgrades together; see [docs/UPGRADING.md](docs/UPGRADING.md) (#40).
- Environment variables are spelled `CAIRNMIND_*`. The earlier `DEVBRAIN_*` spelling is still read; for a configuration variable the new one wins when both are set, and `cairnmind doctor` reports a pair that disagrees. A new installation keeps its data in `~/.local/share/cairnmind`; an existing `~/.local/share/devbrain` is used where it is and is never moved or copied. The launcher gives coding clients both spellings of the session variables, so project files written by earlier versions keep working (#40).
- `cairnmind impact PROJECT --since COMMIT` lists the decisions, facts and tasks linked to the files and symbols changed since a commit, each with the reason for the link: the record's evidence names the changed file or definition, or the record cites a snapshot of the changed file. It is read-only and asks no model (#8).
- After an edit, indexing opens only the files whose size, times or inode changed since this process last indexed them, and writes only the graph rows that differ instead of replacing the whole graph. On a project with 5,000 files the indexing part of the first question after editing one file fell from 159 s to about 1 s. The first indexing after the service starts still reads every file (#62).

## 0.9.0

The first release under the name Cairnmind.

- The Python module is `cairnmind`; `devbrain` remains as an import alias for one release, so hooks and MCP entries that start `python -m devbrain` keep working wherever the Python they name is still installed. After the installer has replaced the earlier `devbrain` uv tool, run `cairnmind install <project>` for each project as the installer lists them; that also rewrites the entries to the new module name. Environment variables, the data directory and the portable memory format keep their `devbrain` names for now (#40).
- The code fingerprint behind acknowledgements, questions and check evidence no longer resolves the path of every file: whether a directory lies inside the worktree is decided once per directory. On 5,000 files it fell from 0.45 s to 0.18 s, and from 0.91 s to 0.57 s when the files are 100 KB each. File content is still always read, so any edit changes the fingerprint; the README documents the cost for large worktrees (#24).
- A question no longer re-indexes an unchanged project: the tree is compared by file sizes and times without opening the indexed files, and the answer cache stamp is a change counter instead of a scan of seven collections. On a project with 5,000 files the indexing part of a question fell from 52 s to 0.05 s. The background scan of the service skips unchanged projects the same way. A question still hashes the worktree once for its code identity (#24), and after any edit the whole project is indexed again (#62). A directory that cannot be listed is now reported instead of having its files deactivated (#23).
- The help page of every command and the messages written in the command line module are in English. Messages raised by the workspace, cockpit and service modules are still Polish (#37).

- **Conflicts** view in the memory inspector: pairs of facts or decisions that extraction marked as possibly contradictory are shown side by side with evidence times, scope and sources. You resolve a pair by letting one finding supersede the other, by keeping both for different scopes, or by dismissing the alarm; every decision is saved with an audit note and no source is removed (#7).
- The audit note of a review or of a conflict decision no longer counts as evidence time. A record gets the corrected time the next time it is written; the Conflicts view reads the times from the sources directly.
- The memory inspector shows when a record's evidence was stated or observed, and warns when a record replaced a finding with newer evidence (#39).
- Records have a derived evidence state: `anchored`, `evidence_replaced` (with whether a verified quoted passage survives), `orphaned`, or `unverified` for imported file evidence before local indexing. The memory inspector shows it, a newly prepared resume packet warns about orphaned and changed records without blocking the resume, and `cairnmind memory orphans PROJECT` lists them. The state is computed when read and is not stored, so snapshots and the portable state hash do not change (#6).

No model is asked and the command does not start the service; every line below the title and the legend is marked `machine` or `reported` (#3).
- `cairnmind memory show PATH` prints a portable snapshot's records and plans with their source addresses as text, with `--kind`, `--status` and `--grep` filters. It needs no Java, engine, model or service and writes nothing; inside a coding session the running service authorizes the package first (#2).

- The package moved to the repository root: after cloning, run the installer and the tests from the top-level directory. The contract documents are in `docs/`.
- **Renamed to Cairnmind.** The repository moved to `piotrwozn/cairnmind`, the package is `cairnmind` and the command is `cairnmind`; `devbrain` remains an alias for a transition period. The installer removes an earlier `devbrain` uv tool, keeps your memory, and lists the `cairnmind install <project>` commands that reconnect existing projects. Data paths, environment variables and the portable memory format keep their `devbrain` names until a compatible migration (#40).
