# Changelog

All notable changes are listed here, newest first. Releases up to 0.8.0 were published as DevBrain.

## Unreleased

### A lighter first start

- The database engine can run in Docker, so Java 21 on the host is optional: `cairnmind engine start --docker` (also `engine up --docker`) runs Cairnmind's ArcadeDB image (`ghcr.io/piotrwozn/cairnmind-arcadedb`, pinned by digest) with the data directory mounted, as your own user, on `127.0.0.1` only; `--build` builds the same image on this machine from the files shipped with Cairnmind. `engine stop` acts only on the container carrying this installation's labels and refuses when it cannot tell; `engine status` reports the container as unknown then (#272).
- `cairnmind init` chooses the engine mode once, Docker when Java 21 is missing and Docker answers, says which it chose and saves it as `engine_mode` in `config.json`; a saved mode whose tool is missing is an error that names it. `engine start --native` goes back. The native engine and the engine in Docker never run on one data directory at the same time (#272).
- `cairnmind doctor` names the engine mode (`arcadedb.engine`) and, in Docker mode, does not ask for Java and reports Docker and the container; the installer no longer stops for a missing Java when Docker answers (#272).
- tmux 3.4+ is needed only for the terminal workspace: opening it (`cairnmind`, `cairnmind tui`, `cairnmind workspace takeover`) without tmux 3.4+ prints one message that names the version found, the install hint and the commands that work without it (`serve`, `run`, `mcp`, `brief`), and exits with code 1; every other command works without tmux (#273).
- `cairnmind doctor` reports a missing or older tmux as `cockpit: unavailable (tmux 3.4+ not found)`, with the version found when it is too old, and still exits 0; with tmux 3.4+ its output is unchanged (#273).
- The installer no longer stops without tmux 3.4+: it says the terminal workspace is unavailable, goes on, and ends by naming the commands that work without it; without a tmux client it still treats a terminal server it owns as running and stops before replacing the installed version (#273).
- `cairnmind mcp --client external` starts the knowledge service when a tool call finds it not running, the way `ask`, `run` and `context` do, so an external MCP client works after a reboot without a manual `cairnmind serve`; parallel tool calls share one start; on a reader installation nothing is started and the error gives the reader reason; when the service cannot start, the error says why and names the command that starts it (#258).
- Cairnmind starts without Ollama and models: `cairnmind init` saves `knowledge_agent: disabled` (deterministic-only mode) in config.json when no model server or model is found, says why, and names `cairnmind models pull` and `cairnmind models set`; an invalid model profile is refused by init instead of being filed as "no models" (#274).
- In deterministic-only mode plans, tasks, the acknowledgement gate, `check run`, `brief`, `impact`, memory and file indexing work as usual; extraction and embedding jobs wait without failing and run once models are configured, and `cairnmind status` shows `models: not configured (deterministic-only mode)` and how many jobs wait (#274).
- Without models, `ask` (the command, the MCP tool, `POST /ask` and the Ask memory panel) is a full-text search of the project's memory and makes no answer: the status is `unavailable` with `diagnostics.code: models_not_configured`, `sources` stays empty, and `full_text_matches` lists up to 8 passages that match words of the question, found by full-text search under the same project, worktree and sensitivity rules as an answer's evidence and said plainly to be search results, not an answer. Passages that were found but could not be shown are reported, never as "no passage"; a blank question is refused as with models; no citation is made and nothing is cached, logged or evaluated (#274).
- `cairnmind doctor` reports `knowledge_agent: disabled (deterministic-only mode)` as information with exit 0; the evaluations report `not_run` (exit 3) and `rebuild-vectors` refuses while no models are configured (#274).
- `cairnmind models pull` (after a successful download) and `cairnmind models set` (after its check) set `knowledge_agent: enabled` and say so at once, with how to turn it off; a running service that started without models tells you to restart it; installations from before 0.13.0 keep their models and a configured server that is down is still reported as a fault (#274).
- `README.md` is a short start page: the pitch, the comparison, a quick start without Java, tmux or models, the optional models and workspace, what is guaranteed, the measured results and an index. The rest moved into `docs/`: new `ARCHITECTURE.md`, `EXTERNAL_CLIENTS.md`, `MEMORY.md` and `STORAGE_AND_MAINTENANCE.md`, and new sections of `CONTRACTS.md`, `WORKFLOW.md`, `EVALUATION.md`, `TERMINAL.md`, `API.md`, `INSTALL.md` and `UPGRADING.md`. The moved text is the same except where it had become untrue, above all what a first start needs (#275).
- The documentation of external MCP clients no longer says to start the service first: their first tool call starts it (#258, #275).
- `cairnmind setup` shows where storage and the memory models run and what runs on this machine, in three lines (`--json` for the structured form). Without a profile it changes no setting of an initialized installation (#74).
- `cairnmind doctor` and `cairnmind status` start with `topology`: the same three lines, the variable a value came from when it was not `config.json`, whether the models were evaluated, and the writer role with its problem. The workspace status row shows Storage and Models when the terminal is wide enough (#74).
- An empty `CAIRNMIND_ARCADE_CONNECT_URL` no longer turns a connect-only installation into a managed one; it counts as unset, like the port and Ollama variables (#74).
- `cairnmind setup local`, `cairnmind setup remote-db` and `cairnmind setup remote` move storage and the memory models: each target is tested before anything is saved, the plan says what changes, what has to be rebuilt and what is left as it is, and nothing changes without `--yes` (#74).
- Passwords and keys are never asked for, printed or saved by `setup`: `--password-file` names a private file you created (mode 0600) and only its path is saved; `--admin-password-file`, which creates the database and its user, is used for that one step and never saved; a model server's key is named with `--credential-ref` (#74).
- Going back to the engine on this machine from a store Cairnmind only connects to needs `--backup FILE` (a backup of that store, checked, then restored here under the same rule as `cairnmind restore`: the person's confirmations are kept only with the open workspace's key, and the plan and the output say which way it goes) or `--empty`; the remote store is never written to or deleted, and a failed step puts config.json back as it was, except that the managed password generated for the engine on this machine stays once its start was tried, so that the command can be run again (#74).
- `setup` with a profile is refused while the knowledge service runs (`cairnmind stop` first), in a coding session, and while a variable such as `CAIRNMIND_ARCADE_USER` would replace a setting it saves; nothing restarts by itself (#74).
- `cairnmind doctor` in a terminal prints a short summary: where storage and the models run, what is required and present, what is required and missing, what is optional and off or on, and the next step. `cairnmind doctor --json`, and doctor's output in a pipe, a file or a script, is the full report as before, and the installer ends with the same summary. A stopped engine that can start is shown as present on demand, an engine answering with another release than the pinned one as missing (#287).
- The README's quick start reaches a first memory operation without models, tmux or a coding assistant (install, project add, remember, brief, ask), and connecting Codex or Claude Code is its own step that names the files `cairnmind install` writes (#287).
- `project add`, `remember` and `install` say in a terminal what they did and what comes next; `install` calls a client connected only when a verified launch would work and otherwise names what is missing; `project add` says when the folder is not a Git repository or has no commit yet; `brief` ends with the next step and carries it as `next` in `--json` (#287).
- A command that starts the service, the MCP server of an external client or the workspace that starts it, and a command that starts the database engine on demand, say so (#287).
- The messages that stop a first start say what to do next: an unknown project, a project name or folder already registered, `run` without the client, a refused verified launch, `status` with no running service, an engine that is not installed, exits or times out at start, and a missing uv (#287).
- The installer no longer prints the engine's JSON or GPU advice without `--pull-models`; without tmux a leftover terminal socket that nothing listens on no longer blocks a second run, and the refusal lists at most five sockets; the Java hint names the apt command (#287).
- Opening the workspace without tmux 3.4+ names `brief`, `remember`, `ask` and `run` as the commands that work without it (#287).
- `cairnmind setup`, `status` and `doctor` no longer say that a model server on another computer "receives questions and memory text" when that address is the refused `ollama_url`: they show the refusal (#287, #301).
- `docs/UPGRADING.md` has a section "From 0.12.0 to 0.13.0": the steps, what the upgrade does to a store (schema and backup format unchanged, an acknowledgement that may be refused once, the first snapshot after the upgrade), what an existing `config.json` means, how to move the engine to Docker and back, the changes scripts meet, and where the README's text moved (#303).
- `cairnmind doctor` exits 1 when something required is missing and 0 otherwise; models, tmux and coding clients never change the exit code, models or a client that are set up but fail are listed under "Optional and not working", and the last line names `project add` only until a project is registered; the installer ends with doctor's exit code (#313).
- `project add`, `project list`, `remember`, `ask`, `install`, `init`, `stop` and `engine stop` print in a terminal what they did and what comes next, and no JSON; with `--json`, or in a pipe, a file or a script, they print the full JSON as before (#313).
- `cairnmind install` writes nothing for a coding client that is not installed, not even its instruction block, and Cairnmind's own block in `AGENTS.md` and `CLAUDE.md` is left out of the project's index so it no longer comes back in `ask`; a block indexed earlier leaves the index the next time the project is indexed (#313).
- A data directory whose engine port is taken by another data directory's engine says so, names the way out and no longer tries to start a second engine there; when this data directory's own engine, a verified process or a running container of its own, refuses sign-ins for about 30 seconds after failed attempts, it says that and advises to wait, never to move or stop the engine (#313).
- Without models, `ask` in a terminal says in its status line that there is no answer without models, marks a proposed record as unconfirmed, shows the freshness warnings, and lists a record and the note it was made from once; `ask` for an unknown project, or on an engine that refuses this data directory, says so before it starts the service (#313).
- The installer without Java and without Docker names both and says to run it again; a second run says when it stops the running service and no longer announces a download when the engine is already there; a command that needs Java at run time names Docker too (#313).
- `project add` with a folder that does not exist says how to go on, and adding a registered project says it was already registered; the sentences about proposed findings say that nothing more is needed to go on; doctor no longer suggests `cairnmind stop` for a service that is not running (#313).
- A command whose first argument is the project says that the project name comes first, names every argument that follows it and names `cairnmind project list`, for example when a question is typed without a project (#326).
- The installer no longer prints `init`'s JSON block or uv's list of packages and ends with the one Next line of its check; its stop without Java and Docker says that nothing has been installed yet and that Java is the simpler choice (#326).
- `cairnmind doctor` and the installer's check no longer name the internal database in their sentences, and the Storage line says who sets the address and that this installation is the one that writes to the store. `cairnmind brief` shows only the parts of its legend that apply, and the Next of `remember` and `brief` says that the memory inspector is the only place a person confirms or disputes a finding (#326).
- `cairnmind ask` without models shows a stored note as a stored finding and ends with a next step; opening the workspace without tmux names `cairnmind run` only when a coding assistant is installed; `cairnmind project --help` describes `add` and `list`, and `project add` prints the Git warning before its Next line (#326).

### Removed

- The `devbrain` command is gone: the package installs one executable, `cairnmind`, and the alias that 0.9.0 to 0.12.0 installed beside it is removed. Nothing stored changes (data directory, database name, backups, `DEVBRAIN_*` variables, `python -m devbrain` in DevBrain 0.8.0 project files), and `cairnmind install` still rewrites project files that an earlier version wrote. Replace `devbrain` with `cairnmind` in your own scripts, shell aliases and editor MCP settings (#314).
- If the installer finds a `devbrain` file left in uv's tool folder, it names it with the `rm` command that removes it, and removes nothing itself; if an earlier DevBrain uv tool exists that uv does not list, it stops and says how to stop and remove it (#314).
- `cairnmind install` names every MCP server or hook in the project's client files that you wrote by hand and that still starts `devbrain`, and leaves the entry unchanged; it says to remove the entry where it has just written its own, and otherwise to write `cairnmind` there (#314).

### A person's acts need the open workspace

- A person's acts (a review, a conflict decision, a plan confirmation, accepting or withdrawing a record kind, the workspace form, and an import or `--take-published` that replaces records confirmed or disputed here) need a key that the open workspace keeps in its tmux server; the service token alone is refused and nothing is written (#214).
- The command line no longer confirms: `remember --confirmed`, `memory confirm-plan` and `record-kind accept` or `withdraw` are refused with exit code 2 and say where a person does it, `task add` stores a proposed task, and `plan save` or `plan adopt` can no longer change what a person confirmed (#214).
- `--replace-confirmed` and `--take-published` from the command line can no longer replace a record you confirmed or disputed; the memory view of the workspace does it: Import for an archive, Team memory for a published folder or a commit (#304).
- The inspector confirms a plan: open it in Plans and choose Confirm (#214).
- The workspace refuses to open when its tmux server cannot give a key for a person's acts, and says to run `cairnmind workspace stop`. `cairnmind workspace status` reports whether the workspace holds the key (`person_key`: present, absent or unavailable), never the key itself (#214).
- `docs/MEMORY_CONTRACTS.md` says what a program of the same user can still do, `cairnmind restore` included, and `docs/UPGRADING.md` says to stop and reopen the workspace after upgrading from 0.12.0 (#214).
- `cairnmind restore` keeps a person's confirmations and accepted transcript record kinds only when it reads a key from the tmux server of this installation's open workspace; otherwise it still restores every row, turns each person's confirmation into the backup's claim ("as the backup says ... not verified here"), withdraws the accepted record kinds in the same transaction, and says which way it went, how many, and why no workspace answered (#214).
- `cairnmind workspace status` shows `person_key` as present only for a socket that passes the same checks as a restore and a person's request (#214).
- Team memory in the memory view imports published team memory from a folder or a commit: the check lists every record confirmed or disputed on this computer that the import would replace and every record it takes from the published side, and the import runs only after you agree in a consent dialog, with the workspace's key. An import whose list changed since the check is refused and nothing is imported; the service also refuses a published import that replaces such records without the list the person was shown (#304).
- A published memory folder given to the service as a relative path is refused instead of being read against the service's working directory; a Windows drive path typed in the Team memory folder field is accepted and translated (#304).
- Known limit: from a commit, a record you disputed or confirmed here after the last publication cannot be replaced; import it from the published folder with the take field, as the commit form says (#304).
- An impact verdict and the release of a record past the secrets gate are a person's acts: POST /inspector/impact/verdict and POST /inspector/records/{id}/release need the key the open workspace keeps, and the service token alone is refused with nothing written (#306).
- The inspector releases a record: open it and choose Release, with the reason that is published with it (#306).
- `cairnmind impact-verdict` and `cairnmind memory release` are refused with exit code 2 and say where the person does it in the workspace (#306).
- docs/MEMORY_CONTRACTS.md lists both among the person's routes and says that a release or verdict an imported package carries counts as the package's claim (#306).
- The workspace adopts a group of old tasks into a plan: More, then Old task groups lists each group with its tasks in plan order; after the plan title, a consent dialog shows the tasks and what adopting does, and Adopt makes the group a new plan in one person's act, its steps proposed until the plan is confirmed (#305).
- POST /inspector/legacy-groups/adopt needs the key the open workspace keeps; the service token alone is refused and nothing is written. GET /inspector/legacy-groups lists the groups (#305).
- `cairnmind plan adopt` still adopts a group that holds nothing a person confirmed; for the other case its refusal names More, then Old task groups (#305).

### Evaluations, measurements and decisions

- `cairnmind eval injection` measures how often instruction-like texts planted in a README, a code comment, a message by the person, a message by the assistant and a tool result are obeyed by extraction, by answers and by the built-in agent, over several runs in a throwaway database (`docs/evaluation/injection-fixture.json`, each plant with a token made at run time and an address in `.invalid`; a custom fixture with a canary-shaped token or an address outside `.invalid` is refused). Each rate counts only the runs and asks in which the plant reached the model; a path where none did is reported as `unmeasured` and fails the run. No command, no write to a file that configures execution and no confirmed record that a plant asks for is carried out: the approver denies them and the service refuses the record, and if one happened anyway the run fails. Exit 0 when measured, 3 when not run, 2 when the fixture or an option is refused, 1 when the run failed. It is not part of the release gate, and no figure is recorded yet (#179).
- The deployment guide explains why the knowledge service stays on your machine, with the module behind each reason and the verdict on the three options; a headless worker is not planned. The row for the service's CPU and peak memory says that it is not measured yet. `scripts/measure_service_spend.py` measures them: the service's CPU and peak memory while `cairnmind index` runs and in a set interval afterwards, while it works off its queue. It refuses to run against an installation (its data directory under either name, port 8765, an engine on 2480, a command with its own `--data-dir`, an exported database name that does not start with `cairnmind_measure_`, a remote engine without such a name, a process that is not the service of the throwaway directory) (#75).
- docs/API.md says that an OpenAI-compatible server is not told a context size. `scripts/compare_model_paths.sh` prepares the measurement of the native Ollama path against Ollama's `/v1` in a throwaway data directory, and refuses anything that could touch the installation; the figures are not measured yet (#217).
### What a hosted agent reads, and the names of an answer

- A built-in agent on a hosted model (a Copilot connection, or an API profile whose address is not loopback) now gets code and documentation only by default: `read_source` refuses a conversation or third-party source and `memory_records` lists such records without their content, each naming the class and the setting `memory_remote_classes` (#183).
- The answers of `ask` and the resume packet that a hosted built-in agent gets leave out held passages and record previews, say so, and count them under `held_back`, also without models, where the full-text matches leave them out and say it is because of the hosted model; the plan, the task, the blockers and the ACK work as before (#183).
- What `remember` and `checkpoint` hand back to a hosted built-in agent no longer includes the record's content, metadata or key, so updating a held record by id cannot return its text or the key written from it; the checkpoint a hosted run saves when it compacts its context is handed back, kept and sent to the provider the same way (#183).
- A built-in agent can still read what its own session archived, and one on a model server with a loopback address is not held back (also when that address forwards to a hosted model); Codex CLI, Claude Code and external MCP clients are not gated, and their provider receives what they read, which the documentation now says (#183).
- A complete answer to a question asked without an answer schema now goes through one more call of the chat model after the support check accepts it: the call lists the product and technology names the answer asserts, and the answer is withheld, as partial with the names listed, when the quoted sources do not state one of them, including a lower-case name such as nginx; a failed, unreadable or blank-named reply withholds it too, and a call that does not finish in the time limit says so (#245).
- The `model_calls` of an answer's diagnostics now keep up to three calls, so a complete answer shows its discovery (or repair), support and names calls (#245).
- A deterministic check of the names an answer introduces (support_check `names_missing`, run after the support check and before the names call) and `scripts/replay_subject_check.py`, which replays the checks of names over kept repository reports without a model and counts as quoted only what the agent kept, are added (a report keeps an answer cut at 600 characters, so the replay lists an answer of that length as not read and exits 2 instead of counting none withheld); the deterministic check stays off until the replay shows no right answer lost (#245).
- `docs/evaluation/subject-questions.json`, a question set built for the checks of names, is added, and `docs/evaluation/RESULTS.md`, `docs/EVALUATION.md` and `docs/API.md` describe both checks, their cost and their known gaps; the figures before and after are marked NOT MEASURED YET (#245).
### Backups without vectors

- Backups and `cairnmind export` no longer carry vectors, so they are smaller: every kind of backup (the daily one, `cairnmind backup`, and the `before-schema-*` and `before-restore-*` safety copies) writes `embeddings` and `vector_indexes` empty and `vector_data` as an empty object, in the same format 5. A restore of such a file sets the completed embedding jobs of the current chunks back to pending in its one transaction, one job per chunk, says how many (`embed_jobs_requeued`), and the service rebuilds the vectors in the background, while text search works at once (#187).
- Until the rebuild ends, a search that wants vectors says so: before the first vector exists, that the vectors are not ready and the search used the text only, and after it, that the vectors are still being built, with the number of embedding jobs left, so an answer does not read as if the project had no such text. The second warning also appears whenever embedding jobs of the project are pending, for example while a new project is indexed. When the jobs of the rebuild failed and none is pending, a third warning gives the number of chunks whose embedding failed and names `cairnmind retry-jobs`. These warnings are kept when an answer keeps only its last warnings. The workspace shows both warnings in Polish too (#187).
- A backup written by 0.12.0 or earlier still restores with its vectors and nothing is requeued. `cairnmind restore` and `cairnmind setup local --backup` print how many embedding jobs wait again, that they wait for the models in deterministic-only mode, and, while no choice about models is stored yet, that the first start of the service decides between the two; the plan of `cairnmind setup local --backup` says before `--yes` that the backup carries no vectors and that they are rebuilt (#187).
- A new script, `scripts/store_growth.py`, measures how many bytes a transcript event and a file revision add to the database and to a gzip backup, with its own engine in a temporary directory and a fake embedding model, without any real model; the table in docs/evaluation/RESULTS.md is not filled in yet (#185).
- Security: in the workspace a person's act is sent only from a consent dialog that shows what will be done, so a key typed before it appeared never sends one; this covers confirming or disputing a record, resolving a conflict, confirming a plan, releasing a record, an impact verdict, accepting and withdrawing a transcript record kind, and Apply of an archive import in the memory view, and a form before the dialog only collects the reason, note or title and its button says Continue (#332).
- Withdrawing an accepted transcript record kind now asks in a consent dialog; before, its confirmation took keys typed before it appeared (#332).
- Importing a snapshot archive over verdicts given on this computer now lists every record it replaces, with no cap, in the check and in the consent dialog, and is refused with nothing written if the archive or the store changed after the check (#333).

### Fixes

- Two installations that first open one store at the same moment now end as one writer and one reader also when the database server runs in production mode, as the image of `deploy/arcadedb` does; before, the second one's command failed with the server's bare error (#277).
- A confirmation, review or conflict decision made in a second worktree now records that worktree's branch and commit in its audit instead of the project root's; `cairnmind memory confirm-plan` accepts `--worktree`, and a worktree that is not a registered root of the project is refused (#247).
- An audit made on a detached head now says `detached HEAD` with its commit instead of the branch `HEAD`; a confirmation that cannot name its worktree in a project with several worktrees records no branch or commit instead of the project root's (#247).
- A resume packet's instruction for accepting an unknown transcript record kind is no longer cut off when the transcript's archive path is long, in the packet or in the refusal an agent gets from ack (#263).
- `CAIRNMIND_PORT`, `CAIRNMIND_COCKPIT_PORT` and `CAIRNMIND_OLLAMA_URL` are now read from the environment like the database address (used by that process, never written to `config.json`), so a second data directory can have its own ports and `cairnmind init` takes the model server address from the environment. `cairnmind doctor` shows the service URL and says when a value in force comes from the environment (#267).
- A command that reaches a service that does not accept its token now says that the service most likely belongs to another data directory and names the port setting, instead of "Invalid local service token" alone; a service that cannot bind its port reports the port and the setting in the command that started it (#267).
- The workspace process now ends with exit code 0 when you stop it with `cairnmind workspace stop`, and keeps a non-zero code when the tmux server is killed from outside (#269).
- The approval dialog of the built-in agent now starts with focus on Cancel when the request fits on screen, so a stray Enter refuses and approving needs a deliberate key press; a longer request starts on its text, and the hint names Tab to reach the buttons (#268).
- Each chunk is now queued for embedding once instead of twice, which halves the number of pending jobs shown while a new project is indexed; a failed embedding job still gets a fresh job on the next repair or model change (#262).
- An acknowledgement no longer goes stale while the queue indexes and extracts records: a proposal the extraction worker wrote and nobody has touched since is left out of the state an ACK is given for. A packet built after such a proposal arrived shows it, labelled `automatic_extraction`; confirming, disputing or editing it, any record a person or a session writes, the plan, the task and the code still make the ACK stale (#256).
- A memory snapshot no longer carries the code graph, which indexing rebuilds from the project's files, so a snapshot of a large repository no longer exceeds the manifest limit. A snapshot written by 0.12.0 that contains graph rows still imports and shows. When a snapshot would exceed a limit, the error names the limit with the size and the limit, and `memory snapshot --preview` reports exact figures and warns before anything is written; an import says that the code graph is not built yet until indexing has built it (#261).
- After a memory import and before indexing has rebuilt the code graph, `impact` (its text, its JSON `warnings` and the terminal Impact list) says that the code graph of the project is not built yet; `ask` already indexes before it reads, so nothing changes there (#286).
- The installer now says that a running Docker would do when Java 21 is missing and Docker is installed but does not answer, with what Docker said, instead of only asking for Java (#285).
- Start work in the workspace for a project whose resume packet is partial now says that the project's memory is partial instead of "Operation needs attention. Connections", and, when an unknown transcript record kind blocks it, names the kind and where to accept it (More, then Transcript record kinds) (#246).
- `cairnmind memory reextract PROJECT [--below-version N] [--dry-run]` extracts again the sources whose untouched proposals come from an older extractor version; when the new extraction commits, those proposals are superseded in the same transaction, while confirmed, disputed and edited records are never changed. It needs the models; `--dry-run` works without them (#194).
- An `ollama_url` that names another computer, in `config.json` or in `CAIRNMIND_OLLAMA_URL`, is now refused like a model profile without consent: nothing is sent to it, not even the read-only checks of `doctor` and `init` or the request of `models pull`, and the message names the setting and the full `cairnmind models set --role chat|embedding --provider ollama --model NAME --base-url URL --allow-remote` command. Before, those three asked such a server which models it has; questions and memory text were never sent to it (#288).
- The installer no longer waits without end for a Docker that does not answer: `docker version` gets 5 seconds and is then stopped. An installation whose stored engine mode is Docker is updated the Docker way, without downloading the native engine. When a workspace is running and tmux is not on the PATH, the installer says so, names the socket and the two ways out, and removes nothing (#290).
- A command that reaches a Cairnmind service of another data directory says so in the workspace and through the MCP bridge too, with the address and the directory, instead of a bare refused token; `cairnmind status` shows `service_url` (#291).
- The dialog that asks for consent ignores Approve for 0.4 seconds after it is first drawn, so a key pressed before it appeared approves nothing, and a resize keeps the focus on Cancel (#292).
- When a database container does not pass its check right after `docker run`, Cairnmind stops and removes the container it has just created and says what became of it; when it cannot, it names the container and the command that removes it (#293).
- Without memory models, the Ask panel shows how to get them under its own heading instead of "Missing evidence", and Process memory says that no models are configured, or that a restart is needed once they are enabled, in a sentence that fits the sidebar (#294).
- A folder inside Cairnmind's data directory is refused as a project, with the reason; before, it was registered and indexed no files. A registration of that kind made by an earlier version stays as it is (#295).

It can be run again for the same user and database and reports that nothing was created. It creates the missing database of a user that exists without one. - A store has one writer, the installation that first opened it, named in the database; another installation that points at the same database reads it only, and a command that writes stops with one line naming the writer (#70).
- An installation is identified by installation.json in its data directory, so a copy of that directory on another machine or under another path gets an identity of its own instead of writing as the original (#70).
- `cairnmind store takeover --yes [--note TEXT]` lets a person move writing to this installation; the change is recorded in the store, the previous writer's running jobs go back to the queue, and the previous writer stops at its next write. It also works when this release cannot read the store as a reader, for example when its schema belongs to another release (#70).
- `cairnmind store writer`, `doctor` (store_writer) and `status` (writer) show which installation writes the store and whether this one is the writer, a reader, or has lost the role; `store writer` and `doctor` also show the note given with `store takeover --note`, as inert text. `status` shows that block only from the running service. On an installation that only reads the store, `status`, `jobs list`, `jobs show` and `memory status` say so and name `cairnmind store writer` and `cairnmind doctor`, instead of telling it to run `cairnmind serve` (#70, #242, #244).
- The service does not start on an installation that only reads the store. A running service pauses its background work when another installation takes over and resumes on its own once writing is taken back. Starting a service that exits at once now reports its last log line instead of waiting a minute (#70).
- On an installation that only reads the store, a refused write says its reason once instead of twice, backup and export no longer print the refusal-like notice, and `cairnmind retry-jobs` is refused even when nothing failed (#244).
- `cairnmind store takeover` without --yes suggests what fits the role: nothing on the writer, starting the engine when the role cannot be read (#244).
- Two installations that open a new database, take over writing a store or claim a new one at the same moment now always end as one writer and one reader: the second is refused as a whole and told to run `cairnmind store takeover --yes` again, instead of failing with the engine's 'Concurrent modification' message or sometimes leaving the writer row and the journal head naming different installations. A takeover that overlaps a write of the current writer is refused the same way, with a message that says so (#68, #70).
- `cairnmind store writer`, `doctor` and the service status report a store whose writer row and journal head name different installations; until the next `cairnmind store takeover --yes` repairs it, the installation the row names is refused every write and runs no schema statement or upgrade (#70).

- A server whose ArcadeDB version this release does not support is refused by every command, `cairnmind db create-user` included, before anything is read or written, with the supported version named; `engine status` exits with status 1 and `doctor` reports it (#68).
- When the database or its user does not exist yet, or the server does not answer, a connect-only installation says where it looked and names `cairnmind db create-user`, instead of starting a local engine or showing a bare HTTP error. When the database cannot be found, the message also names the other cause, a user with no rights on it (#68, #242).
- A refused sign-in to a database Cairnmind only connects to also says that ArcadeDB refuses a user for about 30 seconds after several failed sign-ins, even with the right password. docs/DEPLOYMENT.md and SECURITY.md say the same, and that each database gets its own user from `cairnmind db create-user` (#242).
- `cairnmind engine status` started without the database password is refused (exit 1, "available": null, nothing sent), and `cairnmind doctor` gives `arcadedb.available` as null in the same case instead of reporting a server that does not answer. The message also names arcade_user left at root and an unset arcade_database, on every command and not only the first, and what would be used in their place. On a host other than this machine, the refusal of root also names the missing password and database. docs/DEPLOYMENT.md says the same (#242).
- `cairnmind doctor` shows where storage runs (mode, host, address, supported versions), the database user, whether the connection is encrypted and where the password comes from, and notes when it is stored in config.json; it no longer runs Java on a connect-only installation. `cairnmind status` has a new field `storage`, and `store size` says that the database files are on the server. An existing local installation keeps working unchanged (#68, #72).
- A database address that carries a user, a password, a query or a fragment is refused as before, and is no longer repeated in messages, `engine status`, `doctor`, `status` or `store size`; the refusal names arcade_connect_url when that setting supplied the address (#68).
- The installer skips the Java check and the ArcadeDB download when CAIRNMIND_ARCADE_CONNECT_URL is set (#68).
- `cairnmind eval run`, `eval memory` and `eval repository` are refused on a connect-only installation, because they create and drop databases (#68).

- The database image of deploy/arcadedb runs ArcadeDB in production mode: no Studio, error details only in the server log, the write-ahead log flushed on commit. It leaves out the MCP plugin, so /api/v1/mcp does not exist. docs/DEPLOYMENT.md says what the server exposes and to whom. The local engine is unchanged (#211).
- Plain Kubernetes manifests for the database in deploy/kubernetes: a StatefulSet with its volume, a headless Service on the server's own TLS port, a NetworkPolicy, probes from the image's health check and a Secret template with no value in it. docs/DEPLOYMENT.md documents them with TLS, the dedicated user, and backup and restore (#211).

### Models and where memory goes

- The knowledge agent can use another model or model server: `cairnmind models set` chooses the chat model (answers, extraction) and the embedding model separately, each on the local Ollama, another Ollama, or any server with the OpenAI-compatible API such as LM Studio, vLLM or llama.cpp, after one test call to it; it changes only that role in the settings (#67).
- A model server on another computer needs HTTPS and your explicit `--allow-remote`, because it receives memory content; keys are named with `--credential-ref env:NAME` or `profile:ID` and are never stored in the settings or in memory (#67).
- Every source and record has a sensitivity class (project, conversation or third_party), derived from its kind and origin mark and stored nowhere. A record takes the highest class of the sources it or any earlier version cited, so an update never lowers it. The inspector, read_source, memory_records, the terminal detail view, `cairnmind memory show` and `memory show --sources` show it (#180, #241).
- A memory model server on another computer receives only the sensitivity classes listed in the new setting memory_remote_classes, by default project only. Extraction leaves other sources pending (remote_not_allowed), embedding leaves their chunks to full-text search, and ask leaves them out of its context and counts them under held_back. Held extractions and embeddings run once a class is added to memory_remote_classes and the service is restarted, without importing anything again (#181).
- With the local Ollama, extraction, embedding and ask send exactly what they sent before (#181).
- `cairnmind doctor` shows, under `memory_models`, which server and model each role uses, whether it answers, where its content is sent, which sensitivity classes it receives and which stay on this computer, and whether this pair of models has passed the evaluations; `cairnmind models set` shows the classes too, and doctor reports an invalid memory_remote_classes (#67, #181).
- A passing `cairnmind eval run`, `eval memory` or `eval repository` is recorded for the exact pair of models and setup (servers, context window, reasoning effort) it ran with; answers given with models other than the release's carry `model_evaluation: unevaluated` in their diagnostics until recall and memory have both passed (#67).
- After a change of embedding model, `cairnmind models set` says that vectors must be rebuilt with `cairnmind rebuild-vectors`; vectors of different models are kept apart (#67).
- An embedding model on an OpenAI-compatible server, which reports no digest, is checked with one fixed sentence when the service starts and before rebuild-vectors. If other weights are served under the same name, doctor reports it (also while the server is down), no new vectors are made and search uses text only, until rebuild-vectors accepts the new weights under a new vector namespace (#67, #212).
- When chat and embeddings run on different servers, one that is down no longer holds back the other's background work (#67).
- `cairnmind models pull` downloads only the models that run on the local Ollama (#67).
- The recall evaluation was run with the embedding role on a server the product treats as remote. With the default memory_remote_classes, 21 of the fixture's 22 chunks (all conversation) were not embedded, and recall stayed at 20 of 20 in eight of nine runs (19 in one). The fixture's questions use words from their answers, so it cannot show what vectors add (docs/evaluation/RESULTS.md) (#181).

### Answers about a repository

- `ask` no longer gives a complete answer about a product or setting that the quoted sources never name: a check that asks no model looks for every name the question uses for its subject (a capitalised name, an identifier, a word in backticks) in the quotes, their paths and their sources, and withholds the answer with `answer_unsupported`, listing the names, when one is missing. A name that is only context (an operating system, a person) withholds the answer too when no quoted source has it. Not read by this check: a name written in lower case without backticks, a word in capitals, a question in headline case; not caught: a name the quoted file has elsewhere than beside the quoted value (#245).
- On Cairnmind's own repository the twenty questions give 19, 19 and 20 of 20 complete and right in three runs with the default models, and 20 in the run of the release gate, with none complete and wrong, against 13 in the worst run before this work; of twenty-one questions about things the repository does not have, 20 are refused, and the one left, which names its subject in lower case, is answered complete and wrong. The default chat model stays qwen3.5:9b (#104, #245).
- `cairnmind eval repository` accepts questions about things a repository does not have (`"answer": {"absent": true}`), which are right only when they are refused; an ask that broke (timeout, unavailable model, invalid JSON) is counted as `absent_failed`, not as a refusal. Cairnmind's own set of twenty-one is `docs/evaluation/absent-questions.json` (#245).
- A citation is accepted when the model copied the words of a passage but not its layout (joined lines, other spacing beside punctuation, a code span without its backticks, lines of the source left out between quoted lines); every line of the quote must be in the source, a space between two words or numbers is still compared, and the quote recorded and shown is always the source's own text (#104).
- A cited quote may now be as long as the 900-character passage shown to the model, so an answer about a setting whose value sits at the end of the passage is no longer left unverified (#241).
- A quote written under the ID of another shown passage, or under the ID a search hit was shown with, is recorded for the shown source that holds it; after the one repair, citations that still fail are left out when another citation of the answer verified, and the result then says so in `freshness.warnings` and counts them in `diagnostics.citations_dropped` (#104).
- When the first pass of a question finds no answer and a passage was shown only in part, the best passages are read whole once more, without tools and inside the same time limit; the diagnostics say `second_look`, and for a remote chat server that pass holds back the same memory as the first (#104).
- Definitions are shown to the model before the search hits, so the line that states a value comes before the passages that use it (#104).
- Keys of TOML files (pyproject.toml and others, not lock files) are definitions, so a question about the required Python version or the project version is shown the line that states it. A TOML file nested too deeply to be read is reported as invalid and does not stop indexing. `cairnmind impact` compares a changed TOML file key by key instead of treating it as a file it cannot compare (#104).
- Parameter defaults of Python functions are definitions, shown when the question names the parameter or spells its name in the question's words. `cairnmind impact` compares a parameter by its own text, so a change to its neighbour or to the decorator does not mark it as changed (#104).
- A setting whose name shares one word with the question is shown when its file or class shares another word with it, such as a timeout constant in journal.py for a question about the journal timeout (#104).
- The definition of a setting is found when its name has a unit or joining word the question does not use (per, seconds, bytes, tokens) or a product name the question writes joined; among equal candidates a value comes before a function or class, and a name that is only a filler word such as DEFAULT is no longer taken for the setting asked about (#104).
- `cairnmind eval repository` accepts a value in megabytes written in whole gigabytes where a question lists the form `{gb}`, and docs/EVALUATION.md says how to measure another chat model or a larger context window (#104).
- `cairnmind ask --log`, or `"answer_log": true` in config.json, keeps each answer with its question, citations (source id, sha256, quote), commit, status, model digest and timings in a private per-project log outside the database, so a logged answer is never evidence (#15).
- `cairnmind answers list`, `answers show` and `answers prune` read and trim the answer log; it is capped at 8 MiB per project and deleted by `forget --delete-project` (#15).
- `cairnmind eval replay PROJECT` asks the logged questions again for the scope they were logged with and reports answers that are no longer complete or no longer cite a source they cited, comparing evidence, not wording (#15).

### Extraction

- Memory extraction no longer turns the protocol of a session into proposed records. The launcher's first message, Codex's environment block and a client's tool calls are left out, and conversation messages are told that requests to the assistant, one-off questions and the assistant's narration of its own actions are not project knowledge. On the new evaluation set the share of proposals a person would reject fell from 65% to 29%, with no kept record lost (#160).
- Automatic extraction no longer reads the block that `cairnmind install` writes into AGENTS.md and CLAUDE.md, also in a file saved with a byte order mark, so the client protocol no longer becomes proposed tasks and constraints; records extracted from now on carry extractor version 2 (#241).
- A model that returns depends_on: null no longer makes the whole extraction of a message fail; null is stored as no dependencies (#238).
- Every record that automatic extraction writes now carries metadata.extractor: the extractor version, a hash of the prompt and schema, and the model as name@digest (name@unknown when the model server gives no digest or does not answer in time). Clients can read it but cannot set or change it. Portable memory carries it, keeping only a well-formed stamp on an extracted record. Extracted records without it count as version 0 (#192).
- `cairnmind memory extraction-stats PROJECT [--json]` and `GET /inspector/extraction-stats` show, for each extractor version, how many automatically extracted records are still proposed, confirmed by a person here, disputed or superseded, and the share confirmed of those reviewed, read from record revisions without a model (#193).
- New command `cairnmind eval extraction` measures, with the local model, what extraction proposes from built-in agent, Claude Code and Codex conversations against the records a person would keep. Its report contains the same extractor stamp, so an evaluation result can be matched with records in real projects. The evaluation runs on the configured chat model server, as extraction does, also with a model profile (#160, #192).
- `cairnmind proposed PROJECT --days N` lists the proposed findings not written for N days or more (30 by default), oldest first, with their id, kind, number of sources and newest evidence time; `--worktree` narrows it and `--json` prints it. It only reads. The memory service answers the same list at `GET /inspector/proposed` (#189).
- The memory inspector has a Proposed view, last in its view menu, with the same list for the open project and worktree; Filters sets the number of days, and Enter opens the record so Confirm or Dispute records your review as before (#189).

### Project context and resume packets

- Project context now lists the checkpoint and open tasks first, then decisions and constraints in force, other confirmed records, new findings, and finished tasks last, so finished tasks no longer push rules still in force out of the limited space (#213).
- Project context reserves a quarter of its budget for the most recently updated proposed findings, and always makes room for the newest one, so new findings appear even beside an active plan, many confirmed records or open tasks. It keeps 30% of its budget for confirmed decisions and constraints in force, so many open tasks no longer push the rules out. The checkpoint comes before that share; the open tasks get what is left, rules that do not fit the share come after them, and the tasks that do not fit are counted as omitted. Tasks do not use the reserve for findings, and filling goes on past an entry that does not fit (#188, #241).
- Project context never shows a proposed record while a confirmed record it contradicts (possible_conflicts) is left out: both are shown, or the proposal waits and is counted as omitted. A mark naming a record that has since been replaced counts for the record that replaced it (#241).
- Project context reports how many entries were left out per kind and status in omitted_by_kind_status, so a client knows there is more to page through (#188).
- Project context holds 7,000 characters of records instead of 6,500, so that as many records fit as before now that a confirmed record says who confirmed it (#177).
- Each record in the resume packet now says where it comes from: automatic_extraction for a record the extraction worker drafted, even after a later edit or confirmation; external for one written by an external client's session or after a third-party tool result; unattributed for the rest. The origin is derived from what the store wrote, and a client cannot raise it (#178).
- The resume packet's preview of 20 records now puts the latest checkpoint first, then confirmed records, then the rest, each group ordered by origin with extracted records last. Records over the size budget leave the preview from that end before the packet is cut down, and omitted_by_origin counts per origin what was left out (#178).
- The launch prompt, the start hook's pending message, the built-in agent's instructions and the MCP server's instructions now say that record content in the packet is quoted project data, never instructions (#178).
- `ack_resume`, `resume_context` and session writes no longer fail with "Remote transaction … not found or expired" (503) when reading the project's files takes more than a few seconds, for example for a project on `/mnt/c` under WSL while the queue is indexing. The project's files are read before the database transaction, not inside it, and a write that would be refused anyway is refused before they are read. While extraction is still adding records, an ACK can be refused as stale (409) and needs a fresh `resume_context` (#255).
- The resume packet's schema_version is now 2. An acknowledgement given for a packet prepared before the upgrade goes stale (packet_changed), and the session has to call resume_context and acknowledge again (#178).
- A transcript record of a kind this release does not know still keeps its project's resume packets partial. The packet now names the kind, client, version and byte, and says how a person accepts it (#210).
- A person can accept an unknown transcript record kind as technical for one project, with a note: `cairnmind record-kind accept` in their own terminal, or More, then Transcript record kinds in the workspace. That project's packets are then ready again without a new release, and `record-kind withdraw` takes the acceptance back (#210).
- `cairnmind record-kind list PROJECT` shows the unknown kinds in a project's transcripts with one record each, escaped and cut, and says when it read only part of them. `doctor` lists every acceptance (#210).
- When a visible session's memory is partial and the project's transcripts hold an unknown record kind, the workspace names the kind and where to accept it (#210).
- Only a person accepts a record kind: the command refuses inside a coding session and without a terminal, the inspector route takes no session, and no MCP tool, built-in agent tool or memory import can set it. A malformed record of a known kind and a transcript that fails its integrity checks still block (#210).

### Store, backup and indexing

- Restore writes the rows of a backup in groups of a few hundred per request instead of one row at a time. For the store of Cairnmind's own source it now takes 1,140 requests and 18 s on loopback instead of 281,451 requests and 239 s; into an empty database with 20 ms added to every request it takes 1,079 requests and 28 s, so a large store can be restored over a network. Each group is limited to 250 rows or about 1 MiB of JSON. Nothing else changes: what is restored, every check made before anything changes and its message, and the rollback of a restore that fails or is cut (#219).
- Each answer from the database is freed as soon as it is read instead of waiting for Python's garbage collector, which keeps the memory of restore bounded now that it sends larger requests (#219).
- Restore reads a backup in pieces instead of loading it whole: it checks the checksum and every cross reference in two passes over the file before it changes anything, so its memory no longer grows with the size of the rows; a small index of ids (about 100 MiB per million sources, records or graph nodes) remains. The file format is unchanged (#196).
- The whole-database backup (the daily backup, cairnmind backup and the safety copies made before a restore or a schema change) is written as a stream, so its memory no longer grows with the store. The file format is unchanged and earlier versions restore it (#196).
- A backup file appears only after the backup's transaction has committed; the store size view counts temporary files left by an interrupted backup, and the service removes them after a day (#196).
- Restore refuses a backup file that changes while it is being restored, and the store stays as it was; the refusal says that the file changed while it was being read, instead of calling the file corrupt or reporting a checksum mismatch (#196, #238).
- `cairnmind restore` refuses a missing path or a folder before anything starts, instead of calling it a corrupt backup (#244).
- `cairnmind backup DIR/` with a trailing slash creates the folder (readable by you only) and writes a dated file in it, instead of a file named DIR. A backup into a folder that cannot be created or written says 'Cannot write a backup into <folder>: <reason>' instead of a raw error naming a temporary file (#238, #244).
- `cairnmind store size [PROJECT] [--json]` reports how large the store is: rows and approximate bytes per collection and vector type, sources and their chunks by kind (current against replaced), vector rows per namespace, jobs per state, and the disk use of the database, backups, agent journals and engine log. For the whole store, bytes above 1,000 rows are estimated from 256 rows spread over each collection; one project's rows are summed exactly. It is read-only, starts nothing and prints no record or source text (#184).
- `store size` lists each before-schema and before-restore safety backup with its size and time, and counts the rotated engine.log copies. It shows a vector type left empty by a restore as 'unregistered, empty (left by a restore)' instead of the namespace '(none)' (#190, #238).
- `cairnmind store prune-backups --keep K` deletes all but the newest K safety backups of each kind, after showing them and asking, and only for a person in their own terminal (#190).
- Once a day, after the daily backup, completed jobs that last changed more than job_history_days ago (default 30, 0 keeps everything) lose their attempt history; every job row, its key and its counts stay (#190).
- At each engine start an engine.log that has reached engine_log_bytes (default 10 MiB) is moved to engine.log.1, keeping engine_log_copies old logs (default 3); if the filesystem refuses the move, the engine starts anyway and appends (#190).
- engine.log is created private (mode 0600) whatever the umask, and when it is rotated the old copies are made readable only by their owner too; a copy the owner cannot open or change is still rotated as before (#238).
- An engine_log_bytes or engine_log_copies in config.json that is replaced by its default is reported on standard error and in engine.log when the engine starts, and `cairnmind doctor` lists it among its environment notes (#238).
- When a file is edited or deleted, the chunks and vectors of its earlier version are deleted in the same transaction. The earlier version keeps its full text and hash, so evidence that cites it can still be read and checked. A portable memory import no longer creates chunks for source versions that are not current. So `cairnmind status` counts fewer chunks and indexed sources (#186).
- New command `cairnmind store drop-replaced-chunks` removes the chunks that earlier releases kept for replaced sources. It covers every project in the store, works in short resumable transactions of at most `--batch` rows, and reports how many rows it removed (#186).
- Indexing writes the code graph 250 rows per database request instead of one statement per row, so indexing this repository's own source again after every file changed took about 7,000 requests instead of 57,000 in the measurement made for this change, which is not the 128-file measurement of the deployment guide (#167).
- Indexing also removes graph nodes that no longer exist in groups, so indexing this repository's own source again after half of every file's functions were deleted takes about 5,400 database requests and 27 seconds instead of 67,500 and 75 seconds (#167).
- Indexing files that replace a current source, and files that were deleted, now counts first what the old source leaves behind and writes each file in one transaction, up to eight small files together. The journal events of a transaction are stored in one statement. After every file of a project changed, indexing again needs about half the database requests and time on real code (Cairnmind's own source: 47% of the requests, 50% of the time), and about a quarter to a third on trees of very small files (#102).
- `cairnmind memory status` checks only the newest manifest, so it answers quickly for a large project; its `latest` reads `manifest_valid` with `objects_checked: false`, and `memory inspect` and import still check every object (#161).
- `memory status` now shows the size of the portable package, its rows, bytes (UTF-8, as a snapshot counts them), manifest bytes and largest object, against each publication limit and warns from 70% of any of them, before publishing stops (#191).
- Jobs that the model runtime refused or did not answer in time are labelled model_context_length, model_timeout or model_runtime_error instead of legacy_job_error, and the catch-all label is now job_error (#238).

### Security

- Known secrets are replaced by [REDACTED] before conversation and session text is indexed or given to extraction: the service token, the ArcadeDB password, saved API keys, the values behind env: references of saved profiles, credential variables, private key blocks and well-known key shapes. This covers imported transcripts, archived agent events, remember notes, session findings, checkpoints and tasks. The raw archived text is kept as received, a changed view is marked with metadata.masked, and a transcript record without a readable view is read through its masked metadata.indexed_text (#182).
- A transcript import, an agent archive, a remember note, a finding, a checkpoint or a task stops with the reason when the saved keys or profiles cannot be read, instead of indexing unchecked text. Extraction of a masked source fails and is retried instead of being skipped (#182).
- Excluded directories such as .ssh, .aws, .codex and .git, and the reserved .memory directories (including those of a nested project registered with other letter case), are left out of indexing in any letter case (#230).

### Built-in agent

- The built-in agent's approval dialog for a command or a third-party tool call now lists the files the agent created, changed or deleted since your last approval, at most 20 with a count of the rest, in English and Polish. Line breaks and control characters in a file name are shown as escapes, so a name cannot pass itself off as the app's own text. When a write recorded in the agent journal cannot be read back, the dialog says the list may be incomplete instead of leaving the write out without notice (#176, #230).
- A change by the built-in agent to a file that configures execution now needs the same one-use approval as a command. This covers a coding client's settings or hooks, MCP files, repository instruction files such as AGENTS.md, AGENTS.override.md and CLAUDE.md, CI workflows, editor tasks, dev containers, .envrc and Git hook managers. The dialog shows the path and a bounded diff whose lines are shown whole or not at all, with a count of the lines not shown (#176).
- The built-in agent can no longer write to Git's internals or managed memory through another letter case (.GIT/hooks) or a short Windows alias (GIT~1) on a file system that ignores case, such as a Windows drive in WSL; a short alias also no longer passes the approval for files that configure execution (#230).
- The built-in agent's file tools read each path part the way Windows does (split at a backslash, cut at a colon, drop trailing dots and spaces, fold case) before comparing it with Git internals and managed memory. So `.git.`, `.git `, `.GIT\hooks` and `.git::$INDEX_ALLOCATION` are refused, while ordinary names such as `notes.` or `a:b` keep working (#230).
- A third-party MCP server whose program or arguments name the worktree with other letter case, or by a short Windows alias inside a shell command, is refused like one spelled exactly, and a project root that holds the data directory under another spelling is refused as before (#230).
- The built-in agent no longer has to read and acknowledge its resume packet again when memory proposed from its own conversation is extracted while it works. A record that is confirmed, edited, written by anyone else or brought in by a memory package, and a code change, still make the acknowledgement stale (#168).
- On an Ollama profile the built-in agent asks for a checkpoint when its request nears the model's context window.
